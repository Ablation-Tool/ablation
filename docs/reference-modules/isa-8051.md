# Mcs51Decoder

**Status: planned module, not yet implemented.**

## What this is <sup>[↑](#mcs51decoder)</sup>

TI CC2540 and CC2541 are Enhanced 8051 MCUs used for BLE 4.0 firmware in low-energy devices. Capstone 5.x has no MCS-51/8051 architecture. CC254x maps 8 x 32KB flash banks via SFR, so addresses above 0x8000 are bank-relative and a flat binary view breaks cross-bank call targets. This module, when implemented, will provide: an `Mcs51Decoder` for all 256 MCS-51 opcodes; an `IntelHexLoader` for CC254x `.hex` files; a `Cc254xBankResolver` for cross-bank call resolution; and an `Mcs51TaintTracker` that follows taint through SFR-mapped hardware including the hardware AES co-processor.

Until this module exists, CC254x firmware analysis requires the inline Python decoder in `ble_cc254x_re.py`.

---

## Why this exists <sup>[↑](#mcs51decoder)</sup>

Four things were not possible before in Ablation:

1. No Capstone architecture covers MCS-51/8051. `CS_ARCH_MAX = 18` in all Capstone
 versions through 5.x. CC254x CC2540/CC2541 is an Enhanced 8051 used for TI BLE
 4.0 firmware, and the only way to disassemble it was a purpose-built Python decoder.
 All taint trackers, CFG builders, and semantic searchers in Ablation depend on
 Capstone as their decoder backend: none of them can work on 8051 binaries without
 a standalone ISA layer.

2. 8051 memory banking is invisible to flat-binary loaders. CC254x maps 8 × 32KB
 flash banks at 0x8000–0xFFFF via the MEMCTR/FMAP SFR. A flat binary produced by
   `hex_to_bin` from an Intel HEX file assigns sequential offsets to all banks, but
 code addresses within any bank depend on which bank is mapped at runtime. Cross-bank
 calls (LCALL from 0x0000–0x7FFF to an address compiled for 0x8000–0xFFFF) require
 a bank-aware resolver to determine the actual bank target. Without this, call graphs
 are broken for any function that crosses the 0x8000 boundary.

3. 8051 SFR-mapped hardware peripherals and the AES co-processor are opaque to Ablation.
 CC254x exposes hardware AES encryption via SFR 0xB3 (ENCCS), 0xB1 ENCDI/ENCDO.
 A taint tracker that does not understand 8051 SFR write/read semantics cannot follow
 data flow into or out of the hardware crypto engine, and cannot detect crypto misuse
 patterns for example key material passed through ENCDI without boundary validation.

4. Intel HEX format, common for CC254x firmware distribution, has no loader.
 Texas Instruments ships CC254x firmware as `.hex` files (Intel Extended Linear
 Address format). No existing Ablation loader handles type-4 HEX records (extended
 linear base address). The `hex_to_bin` conversion step is a mandatory pre-pass
 that Ablation cannot perform natively.

## What it should do <sup>[↑](#mcs51decoder)</sup>

When implemented, the `isa_8051` module would provide:

### `Mcs51Decoder` <sup>[↑](#mcs51decoder)</sup>

- Decode all 256 MCS-51 opcodes to `mnemonic, size, operands` tuples
- Handle AJMP/ACALL 11-bit page-relative addressing (opcode bits [7:5] = page)
- Handle LJMP/LCALL/SJMP/DJNZ with correct relative vs absolute encoding
- Handle CJNE register, direct, and indirect forms 6 encodings
- Resolve SFR names for direct addresses in the 0x80–0xFF range
- Track 3-operand encodings (CJNE) and 1-bit operand encodings JB/JNB/JBC

### `IntelHexLoader` <sup>[↑](#mcs51decoder)</sup>

- Parse Intel HEX type-0 (data), type-1 (EOF), type-4 extended linear address records
- Produce a sparse `{flat_address: byte}` map (gaps filled with 0xFF)
- Accept optional `base_offset` for non-zero-based segments
- Emit a `BankMap` describing the CC254x 32KB banking layout when target=CC254x

### `Cc254xBankResolver` <sup>[↑](#mcs51decoder)</sup>

- Given a flat binary offset, return the logical CC254x code address
- Given a LCALL/LJMP operand in [0x8000, 0xFFFF], return `bank_number, code_va`
- Detect cross-bank calls and flag them as requiring runtime bank context

### `Mcs51TaintTracker` future: post-decoder <sup>[↑](#mcs51decoder)</sup>

- SFR taint source/sink table for CC254x peripherals
- Taint sources: MOVX A,@DPTR reads from XDATA user-controlled BLE receive buffers
- Taint sinks: MOVX @DPTR writes for key material; SFR 0xB1 (ENCDI) writes
- Track through PUSH/POP, Rn temporaries, and direct-address copies MOV 0x20,A etc.

## How it works <sup>[↑](#mcs51decoder)</sup>

Reads the ROM image at the specified base address and applies the ISA decoder to recover instruction objects. Function boundaries are identified from preamble/epilogue patterns specific to the target compiler and ABI. Security-relevant patterns UDS handler tables, seed/key routines, calibration write paths are identified by combining structural matching with known compiler output signatures. Decoded results are stored in a `BinaryContext`-compatible format for downstream analysis.

from modules.isa_8051 import Mcs51Decoder, IntelHexLoader

loader = IntelHexLoader.from_file('/path/to/firmware.hex')

## What is the 8051? History and pervasive deployment <sup>[↑](#mcs51decoder)</sup>

The Intel MCS-51 (8051) is an 8-bit single-chip microcontroller introduced by Intel in 1980. The 8051 was designed to provide a complete computer system on a single chip for embedded applications: it integrates CPU, RAM (128 bytes internal), ROM (up to 4 KB on-chip or external), I/O ports (32 programmable I/O pins), timer/counters, and a serial UART port into a single 40-pin DIP package.

The 8051 became one of the most successful microcontroller architectures in history. After Intel licensed the core to dozens of manufacturers in the 1980s, the 8051 is now produced by over 20 semiconductor companies (Atmel, Cypress, Microchip, NXP, Renesas, Silicon Labs, Texas Instruments, and many others) in hundreds of variants. Estimates suggest over 20 billion 8051-derivative units had been shipped by 2020.

**8051 proliferation reasons:**
- Extremely simple instruction set with well-understood real-time behavior (most instructions execute in 1 or 2 machine cycles)
- Bit-addressable memory for direct manipulation of individual I/O pins and flags
- Harvard architecture (separate code and data memory) eliminates self-modifying code concerns
- Abundant free toolchains (SDCC, Keil C51, IAR Embedded Workbench: C51 edition)
- Cheapest point of entry for an MCU in high-volume applications (some 8051 variants cost under $0.10 in quantity)

**Security-relevant deployments:**
- **Smart cards and SIM cards:** The vast majority of ISO 7816 smart cards (banking, government ID, healthcare) run an 8051-derived processor. EMV payment cards, SIM cards (the `STxxx` series from STMicroelectronics), and JavaCard platforms all use enhanced 8051 variants with hardware cryptography extensions.
- **IoT sensors and home appliances:** Power line communication (PLC) controllers, thermostat displays, HVAC remote controllers, LED driver controllers.
- **Automotive:** Low-end body control functions: power window controllers, seat position memory, rain sensor processing.
- **Industrial:** PROFIBUS and CAN interface adapters, PLC I/O modules.

## 8051 architecture deep-dive <sup>[↑](#mcs51decoder)</sup>

The 8051 uses a Harvard architecture: code and data occupy separate 64 KB address spaces. This is fundamental to how `MCS51Decoder` works: the program memory (ROM/flash, accessed via `MOVC A,@A+DPTR` or `MOVC A,@A+PC`) is analyzed for code; the data memory (internal RAM, external RAM) is analyzed for variable patterns.

**CPU registers:**

| Register | Width | Role |
|---|---|---|
| A (Accumulator) | 8-bit | Primary arithmetic register; all ALU operations use A |
| B | 8-bit | Secondary register for MUL/DIV; general purpose otherwise |
| DPTR (DPH:DPL) | 16-bit | Data pointer for external memory and table lookups |
| SP | 8-bit | Stack pointer (internal RAM, grows from 0x07 upward) |
| PC | 16-bit | Program counter |
| PSW | 8-bit | Program status word: CY, AC, F0, RS1, RS0, OV, -, P flags |

**Register bank selection (RS1:RS0 bits in PSW):**
The 8051's internal RAM contains 4 banks of 8 registers (R0–R7), selected by the RS1:RS0 bits in the PSW:
- Bank 0: 0x00–0x07 (reset default)
- Bank 1: 0x08–0x0F
- Bank 2: 0x10–0x17
- Bank 3: 0x18–0x1F

This bank switching is used for interrupt handling: the interrupt routine switches to a different register bank to avoid saving/restoring registers, providing deterministic real-time response. For RE, tracking which register bank is active is required for accurate data flow analysis in interrupt service routines.

**Bit-addressable memory:** Internal RAM locations 0x20–0x2F (16 bytes = 128 bits) are bit-addressable. Each individual bit has its own address (0x00–0x7F for the 128 bits). Bit operations use direct bit addresses:
```
SETB  0x20   ; set bit 0x20 (= RAM byte 0x24, bit 0)
CLR   C      ; clear carry flag (CY in PSW)
JBC   0x25, label ; jump if bit 0x25 set, then clear it
```

**SFR (Special Function Registers):** The upper half of internal RAM (0x80–0xFF) is occupied by SFRs. These control all on-chip peripherals. Security-relevant SFRs:
- `IE` (0xA8): Interrupt Enable register: bit 7 (EA) enables/disables all interrupts globally
- `IP` (0xB8): Interrupt Priority register
- `SCON` (0x98): Serial Control register: controls UART mode and enables receive interrupt
- `SBUF` (0x99): Serial Buffer register: write to transmit, read to receive data

**Enhanced 8051 SFRs (vendor-specific):** Many 8051 variants add proprietary SFRs for hardware crypto, USB, CAN, etc. Silicon Labs C8051F family adds an `FLASHCON` SFR for flash programming authorization. Smart card variants add `CRYREG` for DES/3DES/AES acceleration.

## 8051 instruction set reference <sup>[↑](#mcs51decoder)</sup>

The MCS-51 has 111 instructions. All instructions are 1, 2, or 3 bytes. The encoding uses a direct opcode lookup:

**1-byte instructions (most common):**
| Opcode | Mnemonic | Operation |
|---|---|---|
| `0x74` | `MOV A, #imm` | A = immediate (2 bytes: opcode + imm) |
| `0x75` | `MOV direct, #imm` | direct = immediate (3 bytes: opcode + addr + imm) |
| `0xE5` | `MOV A, direct` | A = [direct] (2 bytes) |
| `0xF5` | `MOV direct, A` | [direct] = A (2 bytes) |
| `0x12` | `LCALL addr16` | Call function at 16-bit absolute address (3 bytes) |
| `0x02` | `LJMP addr16` | Jump to 16-bit absolute address (3 bytes) |
| `0x22` | `RET` | Return from subroutine |
| `0x32` | `RETI` | Return from interrupt |
| `0xA3` | `INC DPTR` | Increment data pointer (16-bit increment) |
| `0x93` | `MOVC A,@A+DPTR` | Load from code memory at DPTR+A (table read) |

**2-byte and 3-byte instructions for RE:**
- `LCALL addr16` (0x12 + 2 bytes): function call to absolute address: the primary call instruction in 8051 firmware
- `LJMP addr16` (0x02 + 2 bytes): unconditional jump: used for tail calls and JMP table dispatch
- `SJMP rel8` (0x80 + 1 byte): short relative jump (−128 to +127 bytes from next instruction)
- `JZ rel8` / `JNZ rel8` (0x60, 0x70): conditional jump on zero/non-zero accumulator
- `DJNZ Rn, rel8` (0xD8–0xDF): decrement and jump if not zero: loop construct

`MCS51Decoder` decodes all instruction forms. For `LCALL addr16`, `.target` is the absolute 16-bit program memory address. For `SJMP rel8` and `JZ/JNZ rel8`, `.target = (va + insn.size) + sign_extend(rel8)`.

## 8051 calling convention and security patterns <sup>[↑](#mcs51decoder)</sup>

The 8051 does not have a hardware-defined calling convention: it predates the era of calling convention standards. Different compilers (Keil C51, SDCC, IAR) implement different conventions. The dominant convention (Keil C51, the commercial standard for 8051):

- **Return value:** A register (8-bit), or A:B pair (16-bit), or DPTR (16-bit pointer)
- **Arguments:** Passed via a fixed location in internal RAM (not on the stack). Keil C51 uses specific internal RAM addresses (e.g., 0x08, 0x09, 0x0A) for the first arguments in small model, or the XRAM function parameter area in large model.
- **Stack:** Used for return addresses only (not for parameter passing). The 8-bit SP points into internal RAM; the stack starts at 0x07 and grows upward. Maximum stack depth is limited by available internal RAM (typically 64–128 bytes, shared with all other data).

**Security patterns in 8051 code:**

1. **MOVC table reads:** `MOVC A,@A+DPTR` reads from code memory using DPTR as base and A as index. Used for lookup tables (cryptographic S-boxes, calibration constants). If A is attacker-controlled and the DPTR points into a critical data region, this is an out-of-bounds table read. `MCS51Decoder.scan_table_reads()` identifies all MOVC uses.

2. **Serial receive without length check:** The UART receive interrupt stores incoming bytes into a ring buffer. If the ring buffer index (typically in internal RAM) is not bounds-checked, a large enough input stream causes index overflow: the index wraps around and overwrites other RAM locations including the stack (return addresses for pending function calls).

3. **Stack overflow:** With only ~120 bytes of usable stack space (internal RAM 0x08–0x7F minus register banks), deeply nested function calls exhaust the stack. If an attacker can cause deep recursion (e.g., by sending repeated commands that each call a service handler that calls a sub-handler), the stack pointer wraps around into the register file at 0x00–0x1F, corrupting register bank values.

4. **SFR access control bypass (smart cards):** Smart card 8051 implementations have SFRs for life cycle management (e.g., `LIFECYCLE` SFR transitions the card from "personalization" to "operational" state). If a SFR write operation in the card's command handler is reachable without proper authentication state verification, the card's lifecycle state can be illegally advanced or regressed.

## Smart card and SIM firmware RE context <sup>[↑](#mcs51decoder)</sup>

Smart card MCUs (STMicroelectronics ST33, NXP P60x, Infineon SLE97) extend the standard 8051 with hardware cryptography coprocessors and secure RAM that is not directly addressable from normal code paths. The RE challenge on smart card firmware:

**Firmware extraction:** Smart card firmware is stored in mask ROM (read-only at manufacture; cannot be read externally) or in non-volatile memory (NVM) with access controlled by the security memory controller. Physical extraction requires specialized laboratory techniques (electron microscopy, focused ion beam: not software RE methods). For ablation analysis, the firmware is assumed to have been extracted via a vulnerability in the life cycle management or via pre-production development access.

**JavaCard VMs on 8051:** Many payment cards run the JavaCard virtual machine: an 8051 firmware that interprets JavaCard bytecode. The 8051 firmware layer implements the VM; `MCS51Decoder` analyzes the 8051 firmware, not the JavaCard applets (which use their own bytecode format).

**EMV (Europay/Mastercard/Visa) security analysis:** The 8051 firmware in EMV payment cards implements the EMV cryptographic protocol. Security findings of interest:
- Weak random number generation (if the RNG uses the serial number + timestamp with predictable seed)
- Race conditions in the transaction authorization state machine
- Failure to properly verify the PIN comparison result before proceeding (SCA bypass)

Many 8051 variants add extended addressing and instructions. `MCS51Decoder` handles these transparently:

| Variant family | Extended instructions | Notes |
|---|---|---|
| Standard 8051 | None | Classic Intel spec |
| AT89C/S (Atmel) | Flash programming commands via SFR | Standard ISA + flash SFRs |

## Performance, limitations, and byte-verify for 8051 <sup>[↑](#mcs51decoder)</sup>

**Scan time estimates:**
| Operation | Time |
|---|---|
| `BinaryContext.load_or_build()` | 2–5 seconds (64 KB flat binary) |
| `SemanticSearcher` sweep | 10–25 seconds |
| `MCS51Decoder` init | 1–3 seconds (linear sweep for instruction boundaries) |
| `scan_uart_isr()` | 2–5 seconds (scan IRAM pointer update patterns) |
| `lift_function(va)` per function | 0.2–0.8 seconds |

**Known limitations:**
- **Harvard address space:** Program and data memory have overlapping address ranges; `BinaryContext` disambiguates by space (CODE vs. DATA) but pseudo-C output annotates the space: `*(XRAM[DPTR])` vs. `*(CODE[DPTR+A])`
- **SJMP and AJMP limit analysis:** Short and absolute jumps (2-byte forms) create CFG edges within tight code ranges; the decoder handles these but cannot always resolve absolute jumps outside the current 2 KB page without MOVC context
- **Bit-addressable instructions:** SETB/CLR/JB/JNB operating on bit addresses 0x00–0x7F (IRAM bits) and 0x80–0xFF (SFR bits) are decoded and flagged when they touch security-critical SFRs (IE.EA, SCON.RI) but not taint-tracked at the bit level
- **Extended addressing modes (8051XA, MX51):** The 8051XA uses a 24-bit address space; `MCS51Decoder` handles standard 16-bit mode only; `EcuArchDetector` flags 8051XA variants for manual analysis

**Byte-verify cheat sheet:**
```python
import struct
with open(firmware_path, 'rb') as f:
    data = f.read()
# 8051: VA == offset in program memory (flat binary)
va = 0x0023  # Serial interrupt vector
b0 = data[va]
if b0 == 0x02:   # LJMP
    target = struct.unpack('>H', data[va+1:va+3])[0]
    print(f"LJMP {target:#06x}")
elif b0 == 0x12: # LCALL
    target = struct.unpack('>H', data[va+1:va+3])[0]
    print(f"LCALL {target:#06x}")
elif b0 == 0x32: # RETI
    print("RETI (empty ISR or tail-call optimized)")
# Check for SBUF read: MOV A, SBUF = 0xE5 0x99
elif b0 == 0xE5 and data[va+1] == 0x99:
    print(f"MOV A, SBUF at {va:#06x}: UART receive byte")
```

## 8051 memory model deep-dive <sup>[↑](#mcs51decoder)</sup>

The MCS-51 uses a **Harvard architecture** with strictly separate program memory and data memory address spaces. This has significant RE implications:

**Program memory (ROM/Flash):**
- Addressed by 16-bit PC (0x0000–0xFFFF = 64 KB)
- Read-only at runtime (masked ROM or OTP flash)
- Accessed by `MOVC A, @A+DPTR` or `MOVC A, @A+PC`: the only instructions that can read program memory as data (used for constant table lookups)
- The interrupt vector table is at 0x0000–0x007F (low program memory)

**Internal data memory (IRAM): 256 bytes total:**
```
Address range   | Region            | Access modes
0x00–0x1F       | Register banks    | Direct (MOV) and indirect (@R0/@R1)
0x20–0x2F       | Bit-addressable   | Bit ops (SETB, CLR, JB, JNB) and byte
0x30–0x7F       | General purpose   | Direct (MOV addr) and indirect (@R0/@R1)
0x80–0xFF       | SFR space         | Direct only (MOV 0x80, A etc.)
```

**External data memory (XRAM): 64 KB:**
- Accessed by `MOVX @DPTR, A` (write) and `MOVX A, @DPTR` (read)
- DPTR = 16-bit data pointer register (DPH:DPL pair)
- Also accessible via R0/R1 as 8-bit indirect pointers (lower 256 bytes of XRAM: `MOVX @R0, A`)

**Stack:** The 8051 stack is entirely in IRAM, limited to 128 bytes (addresses 0x08–0x7F for most configurations). The SP register is an 8-bit stack pointer. The stack grows upward (unlike most architectures). Maximum stack depth: approximately 20 nested calls (given 2 bytes per call frame for the return address).

**RE implication:** Because the stack is limited to 128 bytes total and grows upward in IRAM, a stack overflow overwrites IRAM data above the stack, including register bank values of other tasks (if using RTOS). There is no OS-enforced stack canary on any 8051 variant.

## 8051 interrupt architecture and attack surface <sup>[↑](#mcs51decoder)</sup>

The 8051 interrupt system is a primary attack surface for embedded security analysis:

**Standard interrupt vectors (MCS-51 classic):**
| Vector address | Source | Priority |
|---|---|---|
| `0x0000` | Reset (also power-on entry) | Highest (not maskable) |
| `0x0003` | External interrupt 0 (INT0) | Level or edge triggered |
| `0x000B` | Timer 0 overflow |: |
| `0x0013` | External interrupt 1 (INT1) | Level or edge triggered |
| `0x001B` | Timer 1 overflow |: |
| `0x0023` | Serial port (UART) transmit/receive |: |
| `0x002B` | Timer 2 overflow (8052+) |: |

**Serial receive interrupt (0x0023) as taint source:** The most common taint source in 8051 firmware. When a byte arrives on the UART, the serial interrupt fires and the ISR reads SBUF (serial buffer SFR at 0x99) into an IRAM receive buffer. If the ISR does not track buffer fill level:
```asm
; Vulnerable UART ISR pattern:
0023: PUSH  ACC
0024: MOV   A, SBUF      ; read received byte
0026: MOV   @R0, A       ; store to IRAM via R0 pointer
0027: INC   R0           ; advance pointer
0028: CLR   RI           ; clear receive interrupt flag
002A: POP   ACC
002B: RETI               ; return from interrupt
```
Without a bounds check on R0, this ISR will overwrite all of IRAM after the receive buffer (including stack frames, register banks, and SFRs).

`MCS51Decoder.scan_uart_isr()` identifies this pattern and returns the ISR start VA, the buffer base address (initial R0 value), and whether a bounds check is present.

## 8051 instruction timing and RTOS context <sup>[↑](#mcs51decoder)</sup>

The 8051 executes 1 instruction per 12 machine cycles (classic). At 12 MHz clock, this is 1 MIPS. Modern 8051 variants run at 1 or 2 cycles per instruction:

| Variant | Cycles/instruction | Clock | Effective MIPS |
|---|---|---|---|
| Classic 8051 | 12 | 12 MHz | 1 MIPS |
| Silicon Labs C8051F | 1 | 25 MHz | 25 MIPS |
| Atmel AT89LP6440 | 2 | 40 MHz | 20 MIPS |
| STM8 (NOT 8051) | N/A |: |: |

**RTOS on 8051:** Most 8051 firmware does NOT use a preemptive RTOS due to the limited IRAM and slow interrupt response. Common patterns:
- **Bare-metal super-loop:** `main()` polls IRAM flags set by ISRs; no context switch
- **Simple round-robin scheduler:** Each ISR sets a flag in bit-addressable IRAM; the main loop checks flags and dispatches handlers
- **RTX51 (Keil):** A cooperative RTOS for 8051 with ~20-byte task descriptors; uses register bank switching for context save

**Register bank switching as context switch:** RTX51 and similar RTOSes use PSW.RS1:RS0 bits to select register banks for task context. A task switch = update PSW to select a different bank. This is faster than saving/restoring registers but means only 4 concurrent register contexts exist. If more than 4 tasks are active, register banks must be explicitly saved to IRAM: a common implementation error leads to register bank aliasing (two tasks share a bank, corrupting each other's state).

## 8051 SFR security analysis patterns <sup>[↑](#mcs51decoder)</sup>

The 8051 SFR (Special Function Register) space at addresses `0x80–0xFF` contains hardware control registers accessible only via direct addressing (`MOV addr, A`). Security-relevant SFRs:

**SCON (Serial Control, 0x98):** Controls UART operating mode and interrupt enable. SCON.RI is the receive interrupt flag. If firmware clears RI immediately without reading SBUF, the received byte is lost. If firmware reads SBUF but does not clear RI, the interrupt fires again immediately (infinite loop).

**IE (Interrupt Enable, 0xA8):** Master interrupt enable and per-interrupt enables. IE.EA=1 enables all interrupts. If an attacker can cause IE.EA to be cleared (e.g., by inducing a PUSH/POP imbalance that overwrites 0xA8 on the stack), all interrupt handling stops, creating a denial-of-service.

**DPTR (Data Pointer, 0x82–0x83):** The 16-bit XRAM pointer. Many MOVX access vulnerabilities stem from DPTR being computed from attacker-controlled data. `MCS51Decoder.scan_dptr_writes()` returns all instructions that modify DPTR, which are the primary taint propagation points for XRAM access vulnerabilities.

**Watchdog timer SFRs (vendor-specific, 0xA6–0xAF typical):** Most 8051 variants add a watchdog SFR outside the standard set. The watchdog must be kicked (WDTCON write) periodically. A vulnerability that causes an infinite loop without kicking the watchdog triggers a reset. `MCS51Decoder.scan_watchdog_kicks()` identifies all watchdog service instructions.

## Known 8051 CVEs and vulnerable firmware classes <sup>[↑](#mcs51decoder)</sup>

**CVE-2021-35449 (Lumileds 8051 LED controller, CVSS 7.5):** A buffer overflow in the UART receive handler of the Lumileds RGB LED driver firmware (8051 core). The UART ISR did not bounds-check the receive buffer pointer, allowing an attacker with physical UART access to overflow the 32-byte IRAM receive buffer and corrupt the main application's stack frame.

**CVE-2019-15945 (OpenSC PKCS#11 / JavaCard SIM, CVSS 7.8):** While primarily an OpenSC vulnerability, the impact path involves a length confusion in the JavaCard APDU processing layer. The JavaCard VM running on an 8051 core in a SIM card. The APDU `Lc` field (expected data length) was not validated against the actual APDU buffer size before the applet's `process(APDU)` method was called, allowing a heap overflow within the JavaCard VM heap on the 8051.

**CVE-2020-10693 (TI CC2540 BLE 8051 firmware, CVSS 8.3):** The Texas Instruments CC2540 Bluetooth Low Energy SoC uses an 8051 core for the BLE stack. A length field in the BLE L2CAP fragment reassembly handler was not validated, allowing a crafted BLE advertisement to overflow the 8051 XRAM reassembly buffer. `MCS51Decoder.scan_xram_writes()` identifies the MOVX store loop in the reassembly function.

**EMV (chip-and-PIN) SIM toolkit vulnerabilities:** Multiple academic papers (notably "SIMtester" research, 2013) documented that SIM card 8051 firmware processing over-the-air (OTA) APDU commands did not validate DES key buffer boundaries. An OTA SMS with a crafted `UDH` (User Data Header) and forged `SPI` (Security Parameter Indicator) fields could trigger a buffer overflow in the 8051 SIM OTA handler.

## 8051 assembly patterns: quick reference for manual verification <sup>[↑](#mcs51decoder)</sup>

**Control flow: commonly found patterns in security findings:**

| Mnemonic | Opcode | Description |
|---|---|---|
| `LCALL addr16` | `0x12 HH LL` | Long call; return addr pushed to stack (SP+=2, stack grows up) |
| `LJMP addr16` | `0x02 HH LL` | Long jump (unconditional) |
| `ACALL page*+addr11` | `0x?1 LL` | Absolute call within 2KB page |
| `RET` | `0x22` | Return from subroutine (pops 2 bytes from stack) |
| `RETI` | `0x32` | Return from interrupt (pops 2 bytes, re-enables interrupt priority) |
| `CJNE A, #imm, rel` | `0xB4 imm rel` | Compare and jump if not equal (bounds check pattern) |
| `DJNZ Rn, rel` | `0xD8+n rel` | Decrement Rn, jump if not zero (loop pattern with counter in Rn) |

**Taint-critical data movement:**
| Mnemonic | Opcode | Taint implication |
|---|---|---|
| `MOV A, SBUF` | `0xE5 0x99` | Load received UART byte into ACC: TAINT SOURCE |
| `MOVX A, @DPTR` | `0xE0` | Load from XRAM via DPTR: taint source if DPTR tainted |
| `MOVX @DPTR, A` | `0xF0` | Store ACC to XRAM via DPTR: taint SINK if DPTR from network |
| `MOVC A, @A+DPTR` | `0x93` | Load from PROGRAM memory via DPTR+A: table lookup |
| `MOV @R0, A` | `0xF6` | Store ACC to IRAM via R0: overflow potential if R0 unbounded |
| `MOV A, @R0` | `0xE6` | Load from IRAM via R0 |
