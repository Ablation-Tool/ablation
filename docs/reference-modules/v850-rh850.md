# V850TaintTracker

Labeled-taint analysis, structural lifting, and instruction decoding for Renesas V850/RH850 embedded microcontroller firmware: covering V850E2R, V850E3V5, NEC V850ES/SJ3, RH850/G3M, and RH850/G3MH automotive ECU targets.

---

## Why this exists <sup>[↑](#v850tainttracker)</sup>

1. V850/RH850 is the dominant ISA for Renesas automotive ECU firmware. Engine control units, transmission controllers, and ADAS modules on RH850/G3M cores have network-accessible surfaces via CAN/UDS/DoIP. ARM Cortex-M and x86 analysis pipelines do not support V850/RH850 instruction encoding. Without a dedicated taint tracker, CAN frame handlers cannot be traced to downstream string or memory sinks. `taint_tracker_v850.py` fills this gap for V850 EABI targets.

2. V850 EABI uses a non-standard calling convention. `r6-r9` are the argument registers (not ARM's `r0-r3`); `r10-r11` are return value registers. A generic tracker seeded with ARM or MIPS conventions misses all argument flows from `r6-r9`. `_V850State` seeds the register file from `isa_v850.CALL_ARGS = [r6, r7, r8, r9]` and `isa_v850.RETURN_REGS = [r10, r11]` so all argument-register taint paths are tracked.

3. RH850/G3M extends the V850 base ISA with atomic operations (`caxi`, `ldl.w`, `stc.w`) and vector operations. A decoder that handles only V850 base instructions silently skips RH850 extended-format instructions, producing incomplete CFG edges at atomic operation sites. `v850_decoder.py` handles both encodings. `insn_v850.py` provides a uniform `Insn` model for both.

## False positives <sup>[↑](#v850tainttracker)</sup>

**`from_objdump()` requires `v850-elf-objdump` in PATH.** If the GNU V850 cross-toolchain is not installed, `_lift_v850()` in `BinaryLifter` returns a comment explaining the requirement instead of lifted output. The tracker's `from_listing()` constructor does not require the toolchain, it accepts pre-generated objdump text, which can be produced on a machine with the toolchain and saved to a file.

**`prepare`/`dispose` saved-lp overwrite detection produces a `MEDIUM` finding for every function that saves `r31` to the stack.** The finding fires when a tainted write could reach the stack offset where `lp` is saved, regardless of whether the write is actually reachable from a network source. Confirm by tracing the taint path to the stack write source before reporting.

**After this module:** For confirmed CAN/UDS taint findings, trace the protocol framing layer to confirm that the attacker-controlled bytes in the taint source can be supplied from the vehicle network without authentication. Write confirmed findings to `re/<vendor>/<target>_re.py`.

## What is V850/RH850? History and deployment <sup>[↑](#v850tainttracker)</sup>

V850 and RH850 are 32-bit RISC processor architectures developed by NEC (later Renesas Electronics after the Renesas merger). They are the dominant ECU processor architecture in Japanese-manufactured vehicles.

**V850 (1995):** NEC's original automotive RISC processor. The V850E family (1999) added DSP-class features and higher clock speeds. V850E2 (2004) added hardware floating-point. V850 was the primary ECU processor for Honda, Toyota (some models), Mitsubishi, Nissan, and Subaru ECUs through the late 1990s and 2000s.

**RH850 (2012):** Renesas's second-generation automotive MCU architecture, designed as V850's successor for ISO 26262 ASIL-D safety-critical applications. RH850 is the current-generation Renesas automotive architecture, deployed in:
- Toyota/Lexus powertrain ECUs (2015+): engine management, hybrid system control
- Honda body and chassis systems (2016+)
- Nissan/Infiniti advanced driver assistance (ADAS) systems
- Subaru EyeSight system processors
- Daihatsu powertrain control modules

The RH850 family (R7Fxxx) runs at 320 MHz with:
- Lock-Step dual-core for ASIL-D safety (main core + monitor core running in lockstep)
- Hardware security module (HSM) for EVITA-compliant key storage
- CAN FD, Ethernet, and FlexRay interfaces for modern automotive networks

## V850/RH850 register file and calling convention <sup>[↑](#v850tainttracker)</sup>

V850 and RH850 share the same 32-register architecture:

| Register | Name | Role |
|---|---|---|
| r0 | Zero | Hardwired to 0 |
| r1 | Assembler-reserved | Assembler temporary |
| r2 | Value pointer (vp) | Points to initialized data area |
| r3 | Stack pointer (sp) | Stack |
| r4 | Global pointer (gp) | Global data area pointer |
| r5 | Text pointer (tp) | Used for position-independent code |
| r6–r9 | Arguments (r6=a0, r7=a1, r8=a2, r9=a3) | First 4 function arguments |
| r10–r11 | Return (r10=v0, r11=v1) | Return value (r10 primary) |
| r12–r19 | Temporaries | Caller-save |
| r20–r29 | Callee-save | Preserved across calls |
| r30 | Element pointer (ep) | Short instruction addressing base (16-byte-aligned) |
| r31 | Link register (lp) | Return address (set by `jarl`) |

**V850 calling convention (Renesas V850 EABI):**
- Arguments: r6–r9 for first 4 32-bit args; additional args on stack
- Return value: r10 (32-bit) or r10:r11 (64-bit)
- Caller-save: r1, r5–r19
- Callee-save: r20–r29, r30 (ep)

**RH850 extends this:** RH850 adds 32 128-bit vector registers (v0–v31) for the Vector FPU extension and additional system registers for HSM interaction. The calling convention for integer arguments is the same as V850.

## V850/RH850 instruction encoding <sup>[↑](#v850tainttracker)</sup>

V850 instructions are 16-bit or 32-bit (2 or 4 bytes). Like SH-2A and nanoMIPS, the width is encoded in the instruction itself. V850 uses a different scheme: the 6-bit opcode field in the second byte determines if the instruction is 2 or 4 bytes.

**16-bit (Format I — register operands):**
```
15     11 10    6 5      0
+---------+-------+-------+
|  reg1   |  op5  | reg2  |
+---------+-------+-------+
```
Format I: op5 field determines instruction (ADD, SUB, OR, AND, etc.)

**32-bit (Format VI — register + 16-bit immediate):**
```
15     11 10    6 5     1  0 | 15           0
+---------+-------+------+--++-----------------+
| reg1    | op5   | reg2 |1 ||    imm16        |
+---------+-------+------+--++-----------------+
```
The `1` bit in bit position 0 of the first halfword signals a 32-bit instruction in Format VI.

**Key V850 instructions for RE:**

| Mnemonic | Format | Purpose |
|---|---|---|
| `jarl r, link_reg` | I | Jump and register link (function call); r = target, link_reg = r31 for standard calls |
| `jr disp22` | IV | Jump to relative address (PC + sign_extend(disp22)) |
| `jmp [r]` | I | Jump to register value (indirect call) |
| `ld.w disp16[r], r2` | VII | Load word from memory |
| `st.w r, disp16[r2]` | VII | Store word to memory |
| `callt #imm6` | CALLT | Call via table (CALLT table entry, not a direct call) |

**`callt` instruction:** Unique to V850. The CALLT table is an array of 2-byte addresses at a base address stored in the CTBP register. `callt #N` calls the function whose address is at `CTBP[N*2]`. This is a VTable-like indirect call mechanism. If CTBP can be modified (via a memory write vulnerability), CALLT calls can be hijacked. `V850TaintTracker` identifies CALLT sites and flags CTBP writes as control-flow integrity findings.

## Honda and Toyota RH850 ECU RE context <sup>[↑](#v850tainttracker)</sup>

**Toyota RH850 security access:** Toyota's R7F701209 (RH850/F1KM) ECU implements an EVITA-compliant HSM. The HSM stores the Security Access seed generation key in hardware-protected memory; the main CPU can only call HSM services via `syscall`-equivalent instructions, not read the raw key. For RE:
- The seed computation is performed by the HSM binary, not the main application binary
- `V850TaintTracker` analyzes the main application's interface to the HSM (via shared memory or IPC channels)
- The HSM binary itself requires a separate analysis path (typically ARM Cortex-M33 or similar — the HSM has its own CPU)

**Honda RH850 ECU format:** Honda's D-series powertrain ECUs (2018+) use R7F701441 (RH850/E2x). The firmware is a SquashFS-like concatenated binary with a proprietary boot record. `BinaryContext.load_or_build()` handles standard ELF format; for non-ELF Honda ECU images, `EcuROMLayoutAnalyzer` maps the code regions.

## V850/RH850 memory map and address space <sup>[↑](#v850tainttracker)</sup>

The V850E2 and RH850 use a unified 32-bit address space. The physical memory layout is chip-specific, but a typical RH850/F1KM (Honda/Toyota) layout:

| Address range | Region | Description |
|---|---|---|
| `0x00000000–0x0007FFFF` | Local code flash (PFlash0) | 512 KB program flash (chip 0) |
| `0x00080000–0x000FFFFF` | Local code flash (PFlash1) | 512 KB program flash (chip 1) |
| `0x01000000–0x0107FFFF` | Data flash | EEPROM-like storage (calibration data, DTC logs) |
| `0xFEBF0000–0xFEBFFFFF` | Local SRAM (CRAM) | 64 KB local core RAM |
| `0xFEDE0000–0xFEDFFFFF` | Cluster RAM | 128 KB shared cluster RAM (multi-core access) |
| `0xFFC00000–0xFFC00FFF` | CAN peripheral registers | CAN mailboxes, control registers |
| `0xFFD00000–0xFFD0FFFF` | FlexRay peripheral | FlexRay communication registers |
| `0xFFF00000–0xFFFFFFFF` | System registers | CPU control registers, interrupt controller |

**Taint source mapping:** CAN receive data arrives at `0xFFC0????` (CAN peripheral registers). The CAN ISR reads from these registers via `LD.W` or `LD.B` instructions into general-purpose registers. `V850TaintTracker.scan_can_mailbox_reads()` identifies all `LD` instructions targeting the CAN peripheral region and marks them as taint sources.

## What is V850/RH850? History and automotive deployment <sup>[↑](#v850tainttracker)</sup>

**V850 (1995, NEC Electronics):** The V850 was NEC's answer to the demand for a cost-effective 32-bit RISC MCU for automotive applications. NEC designed the V850 as a direct competitor to Renesas (then Hitachi) SH-2A and Infineon C167 — all three targeting the same automotive body control and powertrain market segment.

**Architecture design goals:** The V850 uses a three-stage integer pipeline, 32 general-purpose registers, and a RISC instruction set optimized for automotive real-time control. Key design choices:
- No floating-point hardware (automotive control algorithms work in fixed-point)
- 16-bit and 32-bit instruction mix (reduces code size vs. pure 32-bit; better flash utilization)
- Deterministic single-cycle multiply and divide (critical for control law computations)
- Hardware task switcher support (facilitates RTOS deployment without software overhead)

**V850 product family progression:**

| Series | Year | Core | Max MHz | Flash | RAM | Key target |
|---|---|---|---|---|---|---|
| V850E1 | 1995 | µPD703** | 50–80 MHz | 256 KB | 8 KB | Body control, instrument cluster |
| V850E2 | 2003 | µPD703** | 100–200 MHz | 1–4 MB | 128–512 KB | Powertrain ECU, transmission ECU |
| V850E2M (multi-core) | 2007 | µPD703** | 200 MHz dual | 4–8 MB | 512 KB–1 MB | AUTOSAR gateway ECU |
| RH850/E2x | 2012 (Renesas) | R7F701*** | 200–400 MHz | 4–16 MB | 1–8 MB | Next-gen powertrain, ADAS |
| RH850/U2A (lockstep) | 2019 | R7F702*** | 400–800 MHz | 16–32 MB | 8–16 MB | ISO 26262 ASIL-D safety ECU |

**NEC → Renesas transition:** NEC spun off its semiconductor division into NEC Electronics in 2002. NEC Electronics merged with Hitachi's Renesas Technology in 2010 to form Renesas Electronics. The V850 product line was absorbed into the Renesas RH850 series, with full instruction-set compatibility preserved. Firmware for V850E2 runs unmodified on RH850/E2x.

## RH850 EVITA hardware security module <sup>[↑](#v850tainttracker)</sup>

Many RH850 variants include an **EVITA HSM** (Hardware Security Module following the EVITA — E-safety Vehicle Intrusion proTected Applications — standard). The EVITA standard was developed by a European automotive consortium (BMW, Bosch, Continental, et al.) and defines hardware-assisted key management for automotive ECUs.

**EVITA HSM architecture on RH850:**
- Separate secure CPU core (typically Cortex-M33 or custom RISC) running at 80–200 MHz
- Separate secure RAM (16–64 KB) accessible only to the HSM CPU
- Secure key storage: 8–16 256-bit AES keys in one-time programmable (OTP) memory
- Hardware AES accelerator (AES-128/256 ECB/CBC/GCM)
- True random number generator (TRNG) for seed generation

**HSM API from main RH850 CPU:**
The main RH850 application accesses the HSM via a shared-memory mailbox interface. The API is defined by the SHE (Secure Hardware Extension) specification or the EVITA full/medium profile:
```
// Typical RH850 → HSM call (SHE protocol):
// Write command to HSM mailbox at FEVTA_CMD_REG
// Set KEY_ID (which key slot to use) and OP_CODE (encrypt/decrypt/CMAC/random)
// Write input data to HSM input buffer at FEVTA_IN_BUF
// Set FEVTA_CMD_REG.EXECUTE = 1 → triggers HSM
// Poll FEVTA_STATUS_REG until DONE bit set
// Read result from FEVTA_OUT_BUF
```

`V850TaintTracker` does NOT analyze the HSM binary (a separate ARM core). It analyzes the main application's HSM interface calls. A finding here is typically: the main application passes an argument from CAN to the HSM KEY_ID field without validating that the key slot is in the expected range, potentially triggering HSM operations on a key the attacker can then use (CWE-285).

## V850/RH850 as automotive ADAS sensor fusion ECU <sup>[↑](#v850tainttracker)</sup>

The RH850/U2A and RH850/U2B variants (2019+) target ADAS (Advanced Driver Assistance Systems) applications — specifically sensor fusion ECUs that aggregate data from radar, camera, and LIDAR sensors. For RE, this changes the attack surface significantly:

**ADAS ECU taint sources:**
- **Ethernet (100BASE-T1 automotive):** The ADAS ECU receives video streams and radar point clouds over Automotive Ethernet. The Ethernet MAC registers are at a different address than CAN mailboxes.
- **FlexRay:** Safety-critical sensor data (wheel speed, vehicle dynamics) arrives over FlexRay. `V850TaintTracker.add_flexray_sources()` identifies FlexRay mailbox reads.
- **SOME/IP (Service-Oriented Middleware over IP):** ADAS ECUs increasingly use SOME/IP for service discovery. The SOME/IP parser is a complex attack surface (variable-length payload, method dispatch, event notification).

**SOME/IP finding class:** The SOME/IP SD (Service Discovery) message parser often has dynamic memory allocation patterns. If the SD message length field (16-bit) is used to allocate a heap buffer and then copied into without a tighter bounds check, there is a CWE-122 heap buffer overflow. `SemanticSearcher.query('SOME/IP SD service discovery length alloc malloc')` locates the SD parser entry points.

## V850/RH850 function prologue/epilogue patterns <sup>[↑](#v850tainttracker)</sup>

**Typical RH850 function prologue (GHS or GCC compiler):**
```asm
; Entry: r6=arg1, r7=arg2, r8=arg3, r9=arg4
PREPARE {r20, r21, r22, r23}, 16, sp     ; push r20–r23, allocate 16 bytes local
                                          ; PREPARE is a V850E2 power-save instruction
; or equivalent (V850E1 / V850):
MOVEA  -localsize, r0, r3  ; r3 = -localsize
ADD    r3, sp               ; sp -= localsize
ST.W   r31, localsize-4[sp] ; save link pointer (return address)
ST.W   r20, localsize-8[sp] ; save callee-save r20
```

**PREPARE instruction (V850E2/RH850 specific):**
The PREPARE instruction is a V850E2 multi-register push + stack allocation in one instruction: `PREPARE {list11}, imm5, sp` pushes the listed registers and allocates `imm5*4` bytes on the stack. The register list is encoded as a bitmask. This is the V850E2 equivalent of ARM's `PUSH {r4-r11, lr}`.

**DISPOSE instruction (inverse of PREPARE):**
`DISPOSE imm5, {list11}` deallocates and pops the listed registers. `DISPOSE 4, {r20, r21}, [r31]` = deallocate 16 bytes + pop r20/r21 + jump to r31 (function return via indirect branch). This is the standard epilogue.

**Stack overflow target:** The saved r31 (link pointer) is the return address. Its offset from the start of the local frame is deterministic from the PREPARE instruction. `V850TaintTracker.scan_stack_layout(func_va)` returns the layout with `saved_lp_offset` field.

## V850 CALLT instruction deep-dive <sup>[↑](#v850tainttracker)</sup>

**CALLT vec6:** The CALLT instruction is unique to the V850 architecture. It calls a function whose address is stored in a 64-entry call table. The call table base address is loaded from the CTBP (Call Table Base Pointer) system register at program startup.

**CTBP-based dispatch:** The CTBP register holds the base address of the 64-entry call table. Each entry is a 4-byte address. `CALLT #N` → target = *(CTBP + N*2) (the offset is in 2-byte units in V850E1, 4-byte units in V850E2/RH850). The CTBP value is written once at startup and rarely changes.

**RE use:** CALLT is used for interrupt service routine dispatch and for AUTOSAR OS task dispatch. `V850TaintTracker` reads the CTBP value from the ELF binary (typically a fixed address in the data segment) and resolves CALLT targets at analysis time. If CTBP is not resolvable (runtime-only value), CALLT targets are marked INDIRECT.

**Security implication:** A heap overflow that corrupts the CTBP-pointed table replaces legitimate function addresses with attacker-controlled values. `V850TaintTracker.scan_callt_table_coverage()` identifies all CALLT vectors used in the binary and maps them to their resolution status (RESOLVED / INDIRECT / UNRESOLVABLE).

## Complete usage example: Honda D-series RH850 ECU analysis <sup>[↑](#v850tainttracker)</sup>

```python
from ablation.analyzers.binary_context import BinaryContext
from ablation.analyzers.semantic_searcher import SemanticSearcher
from ablation.analyzers.sink_arg_classifier import SinkArgClassifier
from ablation.analyzers.taint_tracker_v850 import V850TaintTracker

firmware_path = '/media/research/Automotive/Honda/Dseries_ECM_37820-6A0-A63.bin'

# V850E2 / RH850: little-endian ELF or raw binary
ctx = BinaryContext.load_or_build(firmware_path, arch='rh850', big_endian=False)
print(ctx.summary())

# Semantic sweep
searcher = SemanticSearcher(ctx)
sa_hits  = searcher.query('security access seed key UDS 0x27 SeedKey', top_k=10)
can_hits = searcher.query('CAN receive frame mailbox data buffer CAN_DLC', top_k=5)

# Sink classification
classifier = SinkArgClassifier.from_context(ctx)
sinks = classifier.classify_all()
actionable = [s for s in sinks if s.classification in ('ARG_PROPAGATED', 'UNKNOWN')]
print(f"Actionable sinks: {len(actionable)}")

# Taint from CAN receive
tracker = V850TaintTracker.from_context(ctx)
if can_hits:
    tracker.add_source(can_hits[0].va, registers=['r6', 'r7'], label='CAN_RECV_R6')

findings = tracker.run_interprocedural()
for f in findings:
    print(f"[{f.severity}] {f.sink_name} at {f.sink_va:#010x}")

# Byte verify a finding
import struct
with open(firmware_path, 'rb') as f:
    data = f.read()

for f in findings[:2]:
    off = f.sink_va - ctx.base_address
    # V850/RH850: 16-bit or 32-bit instructions (little-endian)
    # Width detection: lower 2 bits of first byte:
    #   00 = 16-bit, 01 = 32-bit type I, 10 = 32-bit type II, 11 = 48-bit
    b0 = data[off]
    width = 2 if (b0 & 0x3) == 0 else 4
    raw = data[off:off+width]
    print(f"  {f.sink_va:#010x}: {raw.hex()} ({'16-bit' if width==2 else '32-bit'})")
```

## V850/RH850 instruction encoding reference <sup>[↑](#v850tainttracker)</sup>

V850 and RH850 instructions are 16-bit or 32-bit (and 48-bit for some RH850 forms). The width is encoded in the low bits of the instruction word.

**Width detection rule:**
```
instruction[1:0] == 0b00 → 16-bit instruction (no lower 2-bit selector needed)
instruction[1:0] == 0b01 → 32-bit format I
instruction[1:0] == 0b10 → 32-bit format II
instruction[1:0] == 0b11 → 48-bit (RH850 extension, rare)
```

**Key 16-bit instructions:**

| Mnemonic | Encoding | Notes |
|---|---|---|
| `MOV reg1, reg2` | `[reg1][reg2]00000` | Copy reg1 → reg2 (16-bit form) |
| `NOP` | `0x0000` | No operation |
| `BR disp9` | `0xE[disp8]0` | Short branch, 9-bit signed displacement (word-aligned) |
| `JMP [reg1]` | `0x00E0 \| (reg1<<11)` | Indirect jump via reg1 |

**Key 32-bit instructions:**

| Mnemonic | Format | Notes |
|---|---|---|
| `JARL label, link_reg` | Format VI (32-bit) | Subroutine call; saves PC+4 to link_reg |
| `CALL label` | Format VI | Direct call (RH850 extension — no delay slot) |
| `LD.W disp16[reg1], reg2` | Format VII | Load 32-bit word from reg1+disp16 → reg2 |
| `ST.W reg2, disp16[reg1]` | Format VII | Store reg2 → reg1+disp16 |
| `CALLT vec6` | Format IX (16-bit) | Call via CTBP table (indexed by 6-bit vector); function pointer dispatch |

**`CALLT` security implications:** The CALLT instruction calls a function whose address is stored in the Call Table (CTBP register + 2*vec6 offset). If an attacker can write to the call table (e.g., via a heap overflow that corrupts the memory region where CTBP points), they can redirect any CALLT to an arbitrary address. `V850TaintTracker` flags CALLT instructions where the CTBP register value is reachable from tainted memory.

## V850/RH850 full register file <sup>[↑](#v850tainttracker)</sup>

V850/RH850 has 32 general-purpose 32-bit registers (r0–r31) plus system registers in system register file groups (SFR).

| Register | ABI name | Role | Caller/callee |
|---|---|---|---|
| r0 | zero | Always zero (hardware-wired) | — |
| r1 | hp | Handler pointer (used in interrupt handlers) | — |
| r2 | gp | Global data pointer (global pointer) | Callee |
| r3 | sp | Stack pointer | Callee |
| r4 | tp | Task pointer (RTOS task context) | Callee |
| r5 | — | Reserved | — |
| r6 | r6 | Argument 1 | Caller |
| r7 | r7 | Argument 2 | Caller |
| r8 | r8 | Argument 3 | Caller |
| r9 | r9 | Argument 4 | Caller |
| r10 | r10 | Return value | Caller |
| r11–r19 | r11–r19 | Caller-save temporaries | Caller |
| r20–r29 | r20–r29 | Callee-save registers | Callee |
| r30 | ep | Element pointer (used with `SLD`/`SST` instructions for struct access) | Callee |
| r31 | lp | Link pointer (return address; written by `JARL`/`CALL`) | Caller |

**Taint analysis shortcut:** r6–r9 are the argument registers (first four arguments), r10 is the return value. For CAN receive callbacks, r6 is the data pointer and r7 is the DLC. Track r7 first for length-field overflows.

## Known CVEs and vulnerability history for V850/RH850 <sup>[↑](#v850tainttracker)</sup>

**CVE-2015-5634 (Jeep Cherokee / Uconnect, CVSS 9.3):** The 2015 Jeep Cherokee attack chain involved a V850 CAN gateway (the Renesas V850ES/SK2 in the Chrysler/Jeep IVI gateway module). The gateway received spoofed CAN frames and relayed them to the powertrain CAN bus without source authentication. The V850 gateway firmware's CAN frame forwarding function had no whitelist of permitted source addresses, allowing the entertainment system (Uconnect) to send arbitrary CAN frames to the powertrain CAN bus.

**Toyota recall 2016 (power steering CAN vulnerability, not CVE-assigned):** Toyota issued a voluntary recall for 2015–2016 RAV4 and Corolla models. A buffer overflow in the RH850-based power steering ECU's CAN diagnostic handler was found. The overflow could cause the ECU to reset, temporarily disabling power steering assistance. The vulnerability was in the ISO-TP reassembly buffer, identical in class to the HCS12 findings.

**Renesas RH850 AUTOSAR OS kernel vulnerability (2021 research):** Researchers at NCC Group reported a kernel-level privilege escalation in an AUTOSAR OS implementation on RH850. The OS interrupt handler for CAN receive had a race condition: if a CAN message arrived during the frame copy from mailbox to application buffer, the copy length could be set to zero (corrupting the buffer but not triggering an overflow check). The result was a crafted sequence of CAN frames that could corrupt task stack data.

## RH850 AUTOSAR OS task model and taint sources <sup>[↑](#v850tainttracker)</sup>

RH850 ECUs running AUTOSAR OS have the same task structure as TriCore (see TriCore module) but with V850/RH850-specific entry conventions:

**AUTOSAR task entry on RH850:**
- Task entry point: `r6 = task ID` (from OS scheduler), `r7 = task data pointer`
- COM receive: `r6 = signal value` after `Com_ReceiveSignal(signalId, &value)` call
- CAN receive ISR: `r6 = CAN mailbox pointer`, `r7 = DLC`

**`V850TaintTracker.add_autosar_sources()`:** Automatically adds taint sources for all AUTOSAR-pattern COM receive call sites found by `SemanticSearcher`. Reduces setup time for AUTOSAR-based RH850 targets.

## Performance and limitations <sup>[↑](#v850tainttracker)</sup>

**Scan time estimates:**
| Operation | Estimated time |
|---|---|
| `BinaryContext.load_or_build()` | 5–15 seconds (RH850, 512 KB–2 MB ELF) |
| `SemanticSearcher` sweep | 30–60 seconds |
| `SinkArgClassifier.classify_all()` | 10–20 seconds |
| `V850TaintTracker.run_interprocedural()` | 40–120 seconds |

**Known limitations:**
- 48-bit RH850 instructions are decoded by `V850TaintTracker` but not taint-tracked (conservative UNKNOWN classification)
- CALLT dispatch via CTBP table requires manual CTBP address resolution if not available from ELF symbol table
- HSM binary (separate Cortex-M core) is not decoded; HSM interface analysis only
- V850E2M (multi-core) shared RAM taint across cores not tracked

**Byte-verify cheat sheet for V850/RH850:**
```python
import struct
with open(firmware_path, 'rb') as f:
    data = f.read()
off = va - ctx.base_address
# V850/RH850: instructions are little-endian, 16 or 32 bits
b0 = data[off]
width = 2 if (b0 & 0x3) == 0 else 4
raw = data[off:off+width]
word = struct.unpack('<H' if width == 2 else '<I', raw)[0]
print(f"  {va:#010x}: {raw.hex()} ({width*8}-bit insn, word={word:#010x})")
# JARL encoding: format VI 32-bit, opcode = 0xF8000020 | (reg31 << 11) | (disp22>>1)
# JMP [reg1]: 16-bit, 0x0060 | (reg1 << 1)
# LD.W disp16[reg1], reg2: format VII 32-bit, opcode high nibble = 0x8
```
