# x86 Decompilation & Taint Analysis

Analyze x86-64 functions with two complementary paths: `BinaryLifter` produces pseudo-C, while `TaintTracker` traces attacker-influenced registers to security-sensitive calls. x86-32 structural lifting is also available; the taint tracker documented here is x86-64-only.

## Choose the right entry point

| Goal | API | Output |
|---|---|---|
| Recover x86-64 function logic | `BinaryLifter.lift_function_ir()` | IR-backed pseudo-C with optional structure annotations |
| Read a smaller x86-64 or x86-32 function | `BinaryLifter.lift_function()` | Annotated pseudo-C; the x86-32 backend is structural |
| Find source-to-sink flows in x86-64 ELF | `TaintTracker.run()` or `run_interprocedural()` | Taint findings or cross-function paths |

`lift_function_ir()` builds a CFG, lifts to IR, runs optional structure-layout analysis, and emits pseudo-C. It is not a source-code recovery guarantee: types and expressions remain approximations and should be checked against disassembly.

## Decompile a function

```python
from ablation.analyzers.binary_lifter import BinaryLifter

lifter = BinaryLifter.from_path('/path/to/x86_64.elf', arch='x86_64')
print(lifter.lift_function_ir(0x401200))
```

Use `arch='x86_32'` for the 32-bit structural backend. `lift_function_ir()` deliberately falls back to `lift_function()` for architectures without a dedicated IR backend.

`BinaryLifter.from_context(ctx, arch='x86_64')` reuses a `BinaryContext`'s PLT and confirmed function-name overlays. Supply a mapped function virtual address, not a file offset. `lift_function_ir()` catches lifting failures and returns a comment explaining the error, so inspect the returned text rather than assuming every string is successful decompilation.

## Trace taint

```python
from ablation.analyzers.taint_tracker_x86 import TaintTracker
from ablation.analyzers.xref_graph import XRefGraph

xref = XRefGraph.from_path('/path/to/x86_64.elf')
tracker = TaintTracker('/path/to/x86_64.elf', xref=xref)

findings = tracker.run()
for finding in findings:
    print(finding)

paths = tracker.run_interprocedural(depth=4)
flow_findings, flow_paths = tracker.run_flow_sensitive()
```

`TaintTracker` accepts an existing `XRefGraph`, explicit `func_starts`, and optional custom sink names or VAs. Reusing an xref graph is preferable on stripped binaries because it supplies PLT mappings and function boundaries. Without one, the fallback prologue scan is incomplete and may treat file offsets as addresses.

The default policy tracks register and stack-slot taint through common moves, arithmetic, zeroing idioms, address calculations, sources, and sinks. The System V AMD64 argument registers are used. Interprocedural analysis is depth-limited; it is not proof that a path is exploitable.

## Requirements and limitations

- Native lifting and taint analysis use Capstone; binary section mapping uses LIEF when available.
- `lift_function_ir()` has a dedicated backend for x86-64, not x86-32.
- `TaintTracker` configures Capstone for 64-bit x86. Do not use it as an x86-32 tracker.
- Indirect calls, dynamically resolved imports, memory aliasing, and unusual ABIs can interrupt or distort a trace.
- A taint finding identifies a candidate data flow, not reachability from an attacker or exploitability. Confirm the source, destination size, sanitization, and calling convention manually.
