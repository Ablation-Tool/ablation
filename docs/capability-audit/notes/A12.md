## CAP: LLM-Analyst — AgentLoop

- **name**: `AgentLoop` (`ablation/analyzers/llm_analyst/agent_loop.py`, lines 51–325)
- **category**: LLM-assisted analysis / ReAct loop
- **paths**: `ablation/analyzers/llm_analyst/agent_loop.py` (all); `ablation/analyzers/llm_analyst/__init__.py` (lines 1–31)
- **entry point**: `AgentLoop(registry, func_db, product, version, ...).run(func_addr, task)` → `AnalysisResult`
- **what it does**: Drives Claude through a ReAct tool-calling loop for a single function. Claude receives a structured prompt (prior findings + callee names + string xrefs + CFG summary), calls tools iteratively (`get_disassembly`, `get_cfg`, `get_xrefs`, `get_strings`, `get_imports`, `query_func_db`), and terminates by calling `done()` with name/role/confidence/rationale/vuln_notes. Hard budget of `max_tool_calls=10`. Loop detector blocks identical tool+args pairs. `run_patch()` is a single-shot (no tool loop) variant for cross-version diff analysis.
- **inputs/outputs**: `func_addr: int`, `task: str` ('name_function'|'vuln_hypothesis'|'struct_reconstruct'|'patch_analysis'|'exploit_chain'), optional pre-fetched callees/strings/cfg. Returns `AnalysisResult` dataclass (func_addr, name, role, confidence, rationale, vuln_notes, tool_calls, finished, model, task).
- **scope**: x86-64 ELF stripped. Tasks are architecture-aware only through ToolRegistry (which wraps angr). Role taxonomy is Cisco/Fortinet-specific (AAA_DISPATCH, RADIUS_PARSER, CRYPTO_HPKE, etc.).
- **status**: implemented
- **evidence**: no dedicated tests found under `tests/`; integration exercised through ToolRegistry and ContextBuilder unit functions
- **docs**: `docs/reference-modules/llm-analyst.md`, `docs/reference-modules/llm.md`, `docs/reference-modules/llm-analyst-loop.md`. Doc describes `tasks/function_namer.py`, `tasks/vuln_hypothesis.py`, `tasks/struct_reconstructor.py` — all three exist and are confirmed present.
- **limitations**: Default model hardcoded as `claude-sonnet-5` (line 31) — this model ID does not exist in Anthropic's current lineup; should be `claude-sonnet-4-5` or a valid ID. Budget exhaustion produces partial results (confidence 0.1). No multi-function batch orchestration in agent_loop.py itself (batch logic is in tasks/).
- **dependencies**: `anthropic` (Anthropic SDK), `angr` (lazy-loaded in ToolRegistry via `proj` property)

## CAP: LLM-Analyst — ToolRegistry

- **category**: LLM tool dispatch
- **paths**: `ablation/analyzers/llm_analyst/tool_registry.py` (all)
- **entry point**: `ToolRegistry(binary_path, func_db).dispatch(tool_name, args)` → `str`
- **what it does**: Exposes 6 binary analysis tools to the Claude agent: `get_disassembly` (Capstone via angr), `get_cfg` (CFGFast + cyclomatic complexity), `get_xrefs` (CFG predecessors/successors), `get_strings` (CFGFast memory_data + immediate scan fallback), `get_imports` (PLT/simprocedure callees), `query_func_db` (func_id_db by name or role). - **status**: implemented
- **evidence**: no dedicated tests
- **docs**: `docs/reference-modules/llm-analyst.md` (accurate)
- **limitations**: `get_strings` heuristic fallback (`_scan_string_immediates`) may miss strings not referenced by immediate operands. CFGFast build is expensive (~35s on large binaries); shared instance (`self._cfg`) means the first `get_cfg` call bears the full cost.

## CAP: LLM-Analyst — RAGRetriever

- **name**: `RAGRetriever` (`ablation/analyzers/llm_analyst/rag_retriever.py`, lines 25–134)
- **category**: RAG / prior finding retrieval
- **paths**: `ablation/analyzers/llm_analyst/rag_retriever.py` (all)
- **entry point**: `RAGRetriever(func_db).retrieve(func_addr, binary_sha256, callees, role_hint, name_hint)` → `list[dict]`
- **what it does**: Retrieves up to 8 prior confirmed RE findings from `func_id_db` using four strategies in priority order: (1) exact binary SHA256 + VA match, (2) callee-set overlap via LIKE query against `call_targets` JSON column, (3) role-based match, (4) name fuzzy match. Results ranked by callee overlap score, deduped by row id, trimmed to 8 fields for LLM injection.
- **inputs/outputs**: func_addr, sha256, callee names list → list of trimmed dicts (id, name, role, confidence, product, version, notes, va).
- **scope**: `func_id_db` CONFIRMED functions only for callee overlap (LIKE query filters `confidence='CONFIRMED'`).
- **status**: implemented
- **docs**: `docs/reference-modules/llm-analyst.md` (accurate). Note: no vector/embedding retrieval — all SQL-based. This differs from typical RAG architectures; no embedding model dependency.
- **limitations**: LIKE search on JSON column is not indexed; may be slow on large DBs. No semantic retrieval; relies entirely on structural signals (callee names, role, exact match).
- **dependencies**: `func_id_db` SQLite (direct `_con.execute()` calls into private connection)

## CAP: SemanticSearcher

- **name**: `SemanticSearcher` (`ablation/analyzers/semantic_search.py`, lines 295–647)
- **category**: semantic / embedding search
- **paths**: `ablation/analyzers/semantic_search.py` (lines 295–647); `WhiteningTransform` class at lines 241–283 (defined but NOT used)
- **entry point**: `SemanticSearcher.from_context(ctx)` (preferred); `SemanticSearcher(db_path).build_corpus()` + `.query(description, top_k)`
- **what it does**: BERT-backed semantic search over `func_id_db` CONFIRMED/ANGR_INFERRED functions. Builds descriptions via `describe_function()` (name, role, callee names, string xrefs, optional assembly normalization). Encodes with fastembed model. Corpus cached as pickle keyed on `db_hash`. `from_context()` scopes corpus to one binary's functions via `binary_id` + `live_addrs` set, avoiding encoding 296k-function global corpus.
- **inputs/outputs**: Text description query → `list[SimilarFunction]` (name, role, confidence, va, score). Score is raw cosine similarity (no whitening applied).
- **scope**: CONFIRMED + ANGR_INFERRED functions only. Cross-architecture: BinFuse 11-category opcode normalization. Also indexes KNOWN_QUERIES dict for common vuln classes.
- **status**: implemented. **WhiteningTransform is dead code** — class is defined at lines 241–283 but never called by `build_corpus()` or `query()`.
- **evidence**: no dedicated tests; used in integration through corpus_builder + semantic_search pipeline
- **docs**: `docs/reference-modules/semantic-search.md` — **major discrepancy**: doc describes `all-mpnet-base-v2` (768-dim, MPNet) and PCA whitening as a live pipeline stage. Code uses `BAAI/bge-small-en-v1.5` (384-dim, BGE) and whitening is NOT applied. Doc's score threshold table (0.55, 0.40, 0.30) was calibrated for whitened MPNet vectors, not raw BGE vectors.
- **limitations**: WhiteningTransform not wired in — raw BGE cosine similarity is anisotropic; thresholds in docs are not calibrated for the actual model. First corpus build ~9 min on 11k-function binary (fastembed CPU-only).
- **dependencies**: `fastembed` (TextEmbedding, model `BAAI/bge-small-en-v1.5`), `numpy`, `sqlite3`

- **category**: corpus population
- **paths**: `ablation/analyzers/corpus_builder.py` (all)

## CAP: FuncDB (func_id_db)

- **name**: `FuncDB` (`ablation/analyzers/func_id_db.py`, lines 222–574)
- **category**: function identity database
- **paths**: `ablation/analyzers/func_id_db.py` (all)

- **what it does**: SQLite database (schema v2, WAL mode) storing confirmed function names, roles, signatures, and call chains across binary versions. - **scope**: Architecture-agnostic. Role taxonomy defined as constant set `ROLES` (17 protocol-specific roles).
- **status**: implemented. `seed_all()` returns empty dict — designed to be overridden by subclasses.
- **evidence**: no dedicated tests
- **docs**: `docs/reference-modules/libfunc-db.md`, `docs/reference-modules/function-identity-database.md` (not read in full; consistent with code based on usage across other modules)
- **limitations**: `seed_all()` stub does nothing in base class. `match_by_sig()` loads all CONFIRMED functions with non-empty signatures into memory for comparison — O(N) scan with no index pruning beyond `sig_len > 0`.
- **dependencies**: `sqlite3`, `hashlib`, `json`

## CAP: SAXIndex

- **name**: `SAXIndex` (`ablation/analyzers/sax_index.py`, lines 194–357)
- **category**: approximate function search / pre-filter
- **paths**: `ablation/analyzers/sax_index.py` (all)
- **entry point**: `SAXIndex(word_size=8, alphabet_size=8).add_binary(binary_path, ctx)` → `int`; `.query_seq(seq, top_k, max_edit)` → `list[SAXMatch]`; `.query_va(binary_path, func_va)` → `list[SAXMatch]`
- **what it does**: In-memory SAX index for fast approximate function corpus search. Encodes each function's opcode category sequence as a SAX word using histogram-based PAA (Piecewise Aggregate Approximation adapted for categorical sequences — dominant category + frequency per segment → z-score → Gaussian breakpoint bin). Query searches exact word match first, then neighbors within `max_edit` Levenshtein distance (default 2). MINDIST lower-bound pruning available. Persistence via pickle. Intended as a pre-filter before `SemanticSearcher`.
- **inputs/outputs**: Binary path + BinaryContext → indexed entries. Query sequence → `list[SAXMatch]` (binary, func_va, sax_word, seq_len, mindist, edit_dist).
- **scope**: Architecture-agnostic (uses opcode category sequences from `opseq.py`). Alphabet sizes 2–12 supported via pre-computed Gaussian breakpoints.
- **status**: implemented
- **docs**: `docs/reference-modules/sax-approximate-indexing.md` (not read in full; consistent with module docstring)
- **limitations**: PAA adaptation to categorical sequences differs from standard SAX (which uses mean value over real-valued time series). `sax_mindist()` lower bound uses standard SAX formula and may not be tight for categorical histograms.
- **dependencies**: `numpy`, `pickle`, `opseq.OpSeqEncoder`

## CAP: SubsequenceSearcher

- **name**: `SubsequenceSearcher` (`ablation/analyzers/subsequence_searcher.py`, lines 142–361)
- **category**: behavioral pattern search
- **paths**: `ablation/analyzers/subsequence_searcher.py` (all)
- **entry point**: `SubsequenceSearcher.from_path(binary_path, ctx).search(pattern)`, `.search_dtw(ref_seq, threshold)`, `.search_like(ref_va, top_k, mode)`
- **what it does**: Finds all functions in a binary containing a specified behavioral sub-pattern. Three modes: (1) exact category sequence match with optional `None` wildcards, (2) DTW sliding-window approximate match (warp-invariant, window scaled by `window_scale` factor), (3) `search_like()` finds functions similar to an existing function (delegates to DTW mode, optionally pre-filtered by SAX). Includes `pattern_frequency()` for binary characterization and `common_patterns()` for n-gram frequency analysis. Pattern strings parsed via `parse_pattern()` (supports names, abbreviations, wildcards).
- **inputs/outputs**: Opcode category pattern → `list[PatternMatch]` (func_va, binary, match_offsets, seq_len, score). `precompute()` caches all sequences in memory for repeated queries.
- **scope**: All architectures (opcode categories are cross-arch). Cap: 20,000 functions per search.
- **status**: implemented
- **docs**: `docs/reference-modules/behavioral-subsequence-search.md` (not read in full; consistent with module docstring)
- **limitations**: `search_like()` SAX mode (mode='sax') pre-filter is incomplete — code computes SAX word but then still calls `search_dtw()` without actually using the SAX index for pruning (lines 277–279). DTW sliding window has O(N×L×W) complexity — can be slow on large binaries.
- **dependencies**: `opseq.OpSeqEncoder`, `dtw_matcher.dtw_similarity`

## CAP: ProbeRanker

- **name**: `ProbeRanker` (`ablation/analyzers/probe_ranker.py`, lines 137–241)
- **category**: hypothesis engine / probe selection
- **paths**: `ablation/analyzers/probe_ranker.py` (all)
- **entry point**: `ProbeRanker(configuration).generate(hypotheses, executed_kinds)` → `list[ProbeRecord]`; `.top_probe(hypotheses)` → `Optional[ProbeRecord]`; `.plan_report(hypotheses)` → `str`
- **what it does**: Generates and ranks probe candidates for surviving hypotheses by expected information gain (EIG). Formula: `EIG = disagreement × observability × reliability / max(cost, 1e-6)`. Probes with disagreement < 0.05 are skipped (can't distinguish hypotheses). Already-executed kinds get 0.3× observability penalty. Nine probe kinds in catalog: cfg, xref, disassembly, taint, semantic, version, manual, lifter, dynamic.
- **inputs/outputs**: `list[HypothesisRecord]` + optional `executed_kinds` list → ranked `list[ProbeRecord]`. Each ProbeRecord: kind, analyzer name, parameters, EIG, cost, observability, predicted_disagreement.
- **scope**: Probe kinds: cfg (CFGBuilder), xref (XRefGraph), disassembly (Capstone), taint (ARM64TaintTracker), semantic (SemanticSearcher), version (DTWMatcher), manual (analyst), lifter (BinaryLifter), dynamic (DynamicSandbox).
- **status**: implemented. Disagreement estimator is heuristic-only — no symbolic prediction from hypothesis claim fields.
- **docs**: `docs/reference-modules/evidence-scoring-and-probe-ranking.md` — **major discrepancy**: doc describes `HypothesisRecord` with fields `description`, `func_va`, `confidence=ConfidenceState.MEDIUM/LOW` and `ProbeRanker(hypotheses: List[HypothesisRecord])` constructor. Actual code's `HypothesisRecord` uses `kind`, `subject`, `claim`, `status` (not `description`, `func_va`). Doc's usage examples will not run against the actual API.
- **limitations**: Disagreement estimation is heuristic; `_hypothesis_disagreement()` uses status diversity and VA diversity, not actual prediction from hypothesis claim content.
- **dependencies**: `hypothesis_models` (HypothesisRecord, ProbeRecord, ConfidenceState)

## CAP: HypothesisEngine

- **name**: `HypothesisEngine` (`ablation/analyzers/hypothesis_engine.py`, lines 71–421)
- **category**: hypothesis lifecycle orchestration
- **paths**: `ablation/analyzers/hypothesis_engine.py` (all)
- **entry point**: `HypothesisEngine.from_binary(binary_path, architecture, ctx)` → `HypothesisEngine`; `engine.seed(kind, subject, claims)`, `engine.add_evidence(...)`, `engine.plan()`, `engine.step(approved)`, `engine.report()`
- **what it does**: Orchestrates the full hypothesis-driven analysis lifecycle: seed competing hypotheses → accept evidence from any analyzer → score confidence → rank probes by EIG → optionally execute approved probes (Milestone 3 via ProbeAdapters). Sessions persist as JSON in `~/.ablation/sessions/`. `step(approved=True, ctx=ctx_attached)` executes probes via `execute_probe()`. `run_until_stable()` runs up to `max_steps` planning steps until all hypotheses reach terminal states.
- **inputs/outputs**: Binary path + architecture → `HypothesisSession`. `add_evidence()` immediately recalculates confidence. `plan()` → human-readable ranked probe list. `report()` → full session report grouped by status.

- **status**: implemented (Milestones 1–2 complete; Milestone 3 probe auto-execution available when BinaryContext attached)

## CAP: EvidenceScorer

- **name**: `EvidenceScorer` (`ablation/analyzers/evidence_scorer.py`, lines 58–231)
- **category**: scoring / state transitions
- **paths**: `ablation/analyzers/evidence_scorer.py` (all)
- **entry point**: `EvidenceScorer(configuration).score(hypothesis, evidence_items)` → `(confidence, status, notes)`; `.update_hypothesis(hypothesis, evidence_items)` (writes in-place)
- **what it does**: Computes confidence scores and state transitions. Formula: `raw = prior + sum(family_support) - sum(contradiction) - uncertainty`. Diminishing returns: `1/(1+ln(count))` per family (count=1→1.0, count=2→0.59, count=5→0.38). CONFIRMED requires: confidence ≥ 0.75 + ≥1 strong family (behavioral/data_flow/structure) + ≥2 independent families + contradiction < 0.2. Hard contradictions (strength ≥ 0.80 with CONTRADICTS) immediately set REJECTED regardless of support. Uncertainty penalty: 0.1 × len(assumptions).
- **inputs/outputs**: `HypothesisRecord` + `list[EvidenceRecord]` → (float confidence, str status, list contradiction_notes). Writes confidence/support/contradiction/uncertainty scores + status back to hypothesis in `update_hypothesis()`.
- **scope**: Family weights configurable via constructor `configuration['family_weights']`.
- **status**: implemented
- **docs**: `docs/reference-modules/evidence-scoring-and-probe-ranking.md` (scoring formula accurate). `docs/reference-modules/hypothesis-engine.md` (scoring internals section accurate)
- **limitations**: Uncertainty term only considers `len(hypothesis.assumptions)` — if assumptions list is always empty (typical in code usage), uncertainty is always 0.0.
- **dependencies**: `hypothesis_models`, `math`

## CAP: DTWMatcher

- **name**: `DTWMatcher` (`ablation/analyzers/dtw_matcher.py`, lines 163–328)
- **category**: cross-version function matching
- **paths**: `ablation/analyzers/dtw_matcher.py` (all); `dtw_distance()` / `dtw_similarity()` at lines 44–91
- **entry point**: `DTWMatcher.from_paths(v1_path, v2_path).find_homologs(va_v1, ctx_v2, top_k)` → `list[HomologMatch]`; `.score_functions(va_a, va_b)` → `SimilarityReport`
- **what it does**: Cross-version function homolog matching using DTW on opcode category sequences. Sakoe-Chiba band: default 20% of longer sequence length. Local cost: semantic affinity matrix for close category pairs (ARITHMETIC↔LOGIC=0.3, UNCONDITIONAL↔CONDITIONAL=0.5, etc.). Normalized by path length. `find_homologs()` uses histogram L1 pre-filter to reduce candidates to 200 before running DTW. Verdicts: same_era (≥0.85), patched (0.45–0.85), rewritten (0.20–0.45), different (<0.20). Also computes 4-gram Jaccard for comparison.
- **inputs/outputs**: Two function VAs (possibly in different binaries) → `SimilarityReport` (dtw_sim, dtw_dist, jaccard, lengths, verdict). `HomologMatch` includes binary path, similarity, dtw_dist, jaccard, seq_len.
- **scope**: All architectures (opcode categories from opseq.py). Cap: 5000 func_starts for homolog search.
- **status**: implemented (pure numpy, no external DTW library)
- **docs**: `docs/reference-modules/dtw-function-homolog-matching.md` — **discrepancy**: doc shows `HomologMatch` with `confidence: 'HIGH'|'MEDIUM'|'LOW'` field but actual `HomologMatch` dataclass has no such field — uses `similarity` float and `verdict` string in `SimilarityReport`. Also doc shows `score_functions(va_list_v1, va_list_v2)` (list args) but actual signature takes individual VAs; batch is `compare_all(pairs)`.
- **limitations**: `find_homologs()` caps candidate pool at 5000 function starts — will miss homologs in large binaries beyond that index position.
- **dependencies**: `numpy`, `opseq.OpSeqEncoder`

## CAP: MatrixProfileDiff

- **name**: `MatrixProfileDiff` (`ablation/analyzers/matrix_profile_diff.py`, lines 178–369)
- **category**: instruction-level patch diff
- **paths**: `ablation/analyzers/matrix_profile_diff.py` (all)
- **entry point**: `MatrixProfileDiff.from_paths(v1_path, v2_path, window, discord_threshold).diff_functions(va_v1, va_v2)` → `DiffResult`; `.diff_seqs(seq_v1, seq_v2)` → `DiffResult`
- **what it does**: Instruction-level patch diff via Matrix Profile AB-join on opcode category sequences. Computes distance profile: for each position in v1 sequence, finds minimum z-normalized Euclidean distance to any position in v2 sequence. High distance = changed region. Falls back to Jaccard-only result for very short sequences (< window size). Reports `DiffResult` with `list[ChangeRegion]` (unchanged/modified/inserted/deleted), per-version change counts, change_pct, and `is_likely_patched()` heuristic (threshold 15%). Uses STUMPY if available, else pure numpy naive implementation.
- **inputs/outputs**: Two function VAs + binary paths → `DiffResult` with change regions and metadata. `change_summary()` → compact string. `patch_offset_v1()` → first changed instruction index.
- **scope**: All architectures (opcode categories). Max 512 instructions per function.
- **status**: implemented. STUMPY path tested by graceful fallback.
- **docs**: `docs/reference-modules/matrix-profile-patch-diff.md` (not read in full; consistent with module docstring). **Minor discrepancy**: v2 position mapping in `_merge_regions()` is proportional (rough) not LCS — this is noted in code comment but not in doc.
- **limitations**: `_merge_regions()` maps v2 positions proportionally (`round(pos * len_v2 / len_v1)`), not by actual alignment — inserted/deleted regions may be misattributed. STUMPY `stump()` requires minimum sequence length `>= 2*window`; shorter sequences fall back to naive. Naive implementation O(n×m×L) is slow for sequences > 500 instructions.
- **dependencies**: `numpy`, optionally `stumpy`, `opseq.OpSeqEncoder`

## CAP: SigLibrary

- **name**: `SigLibrary` (`ablation/analyzers/sig_library.py`, lines 57–261)
- **category**: behavioral signature matching
- **paths**: `ablation/analyzers/sig_library.py` (all)
