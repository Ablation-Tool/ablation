## 1. PEFABIClobberScanner

- **name:** `PEFABIClobberScanner`
- **category:** ABI Correctness / Vulnerability Scanner
- **paths:** `pef_abi_clobber_scanner.py` lines 1–398; key class lines 268–397
- **entry point:** `PEFABIClobberScanner.from_bytes(code: bytes, base_va: int=0).scan(sink_vas, check_regs, window=32)` → `List[ABIClobberFinding]`; also `from_bytes` + `report(findings)`
- **what it does:** Backward-walks a PPC32 PEF code section from each supplied BL sink VA looking for ABI argument-register clobbers. Returns PLAUSIBLE/SAFE verdicts with stop reason. Fixes three documented bugs from the prior hand-written OpenTransport scanner (ori/addi dest-field asymmetry; addic opcode 12 missing; unconditional branches not treated as basic-block boundaries).
- **inputs / outputs:** Input: raw code section bytes + base VA + list of sink VAs + list of register numbers to check. Output: `List[ABIClobberFinding]` dataclasses (site_va, check_reg, verdict, stop_va, stop_reason); `report()` returns a formatted string.
- **scope:** PPC32 big-endian PEF CFM code sections (Mac Classic / PowerPC). Checks D-form arithmetic, D-form logical, M-form, X-form (opcode 31), I-form, XL-form instructions. Does NOT handle Altivec/VSX.
- **status:** implemented
- **evidence:** No dedicated test file found. Used in OpenTransport analysis context (docstring references sessions 3–11).
- **docs:** `pef-abi-clobber-scanner.md` — not read; `classic-mac-abi-clobber-scanning.md` references this scanner. The `encoding_dag` dependency (`Field`, `Template`) is documented separately.
- **limitations:** Window-bounded backward walk (default 32 insns); does not track cross-function CFG. lmw/lswx/lswi range writes handled conservatively (writes r_dst..r31). No Altivec instruction classification.
- **dependencies:** `ablation.analyzers.encoding_dag` (Field, Template); stdlib struct
- **claims to verify:** Docstring claims three specific bugs fixed vs. hand-written scanner — all three are verifiable in the dispatch-table code (opcode 12 is present at line 121; `_UNCOND` check at line 368 stops at b/ba; separate `_DFORM_LOGICAL` template at line 81). Claims verified structurally.

## 3. PEFBinaryAnalyzer

- **name:** `PEFBinaryAnalyzer`
- **category:** Container Parser / Import Resolver
- **paths:** `pef_binary_analyzer.py` lines 1–496
- **entry point:** `PEFBinaryAnalyzer.from_path(path)` or `.from_bytes(data)` then `.code_bytes()`, `.stubs()`, `.import_by_name()`, `.report()`, etc.
- **what it does:** Parses a PowerPC PEF (CFM) container — section headers, loader section, imported library descriptors, and symbol table. Resolves CFM import stubs via `lwz rX, N(r2)` pattern scan. Returns stub_va→symbol_name dict. Provides code_bytes()/code_base_va() for downstream Capstone/BinaryContext use.
- **inputs / outputs:** Input: raw PEF file bytes or path. Output: `PEFAnalysis` dataclass (sections, imports); `stubs()` returns `Dict[int, str]`; `report()` returns multi-line string.
- **scope:** PPC/CFM PEF containers only (magic "Joy!"+"peff", arch=pwpc). Also validates m68k architecture but does NOT decode m68k sections. Handles 8-library and single-library PEF loader sections.
- **status:** implemented
- **evidence:** No dedicated test file found. Docstring mentions manual analysis of PGPuam sessions 3–11 as motivation.
- **docs:** `pef-binary-analyzer.md` and `powerpc-pef-cfm.md` in reference-modules/. Doc match appears accurate — both mention stub scanning via lwz rX, N(r2).
- **limitations:** Pattern data sections (kind=2) are not unpacked/decompressed. Does not parse XCOFF, ELF, or other containers. Stub scan uses `lwz rX, N(r2)` only; `mtctr/bctr` sequences are not detected as stubs. Negative displacements in lwz stubs are silently skipped (line 314: `if simm < 0: continue`).
- **dependencies:** stdlib struct, pathlib
- **claims to verify:** Docstring says "stub scanning uses the lwz rX, N(r2) pattern (any destination register, not just r12)". Confirmed: mask at line 303–304 checks only opcode=32 and rA=2, leaving rD (bits[25:21]) unconstrained.

## 4. Ppc32Lifter

- **name:** `Ppc32Lifter`
- **category:** Pseudo-code Lifter / Decompiler (Linear)
- **paths:** `ppc32_lifter.py` lines 1–434
- **entry point:** `Ppc32Lifter.from_context(ctx)` then `.lift(func_va, n_insn=150) -> str`
- **what it does:** Linear (non-CFG) PPC32 BE pseudo-code lifter. Tracks register state (r0–r31, CTR) across a single function body. Emits C-like lines tagged with VA. Resolves PLT calls to symbol names with visible argument values. Handles frame alloc (stwu), LR staging (mflr/mtlr), loads (lwz/lwzu/lwzx), stores, arithmetic, and branches as comments.
- **inputs / outputs:** Input: `.text` bytes + text VA + PLT dict + exports dict (via from_context); OR direct constructor. Output: multi-line string of pseudo-code.
- **scope:** PPC32 BE; documented for IBM PPC476 targets. Does NOT do cross-branch data-flow analysis — linear only. Branches emitted as `// branch:` comments.
- **status:** implemented — but **NOTE:** `Ppc32Lifter` in `ppc32_lifter.py` and `Ppc476Lifter` in `ppc476_lifter.py` are functionally identical (same class body, different class name and module header). Ppc476Lifter appears to be a verbatim copy. Neither adds CFG; that is the job of `Ppc476Decompiler`.
- **evidence:** No dedicated test file found.
- **docs:** `ppc476-lifter.md` describes `Ppc32Lifter` from `ppc32_lifter.py` (doc header says "File: ablation/analyzers/ppc32_lifter.py"). `docs/concepts-decompiler.md` contains a **mismatch**: it maps `Ppc476Decompiler` to module `ablation.analyzers.ppc476_lifter` — this is wrong; `Ppc476Decompiler` lives in `ppc476_decompiler.py`.
- **limitations:** Linear-only; does not decode condition expressions (branches are comments). Unrecognised mnemonics fall through as `// mnemonic op` comments. From_context reads `.text` via LIEF, which fails on XCOFF32.
- **dependencies:** capstone (optional; returns error string if absent), lief (via from_context), stdlib struct

## 6. Ppc476Decompiler

- **name:** `Ppc476Decompiler`
- **category:** Decompiler (CFG-aware, typed)
- **paths:** `ppc476_decompiler.py` lines 1–698
- **entry point:** `Ppc476Decompiler.from_context(ctx)` then `.decompile(func_va, n_insn=200) -> str`
- **what it does:** Higher-capability decompiler built on top of Ppc32Lifter semantics but adds: CFG skeleton with back-edge (loop) detection, named stack local variables (`local_0xNN`), typed load/store annotations (uint32_t/uint16_t/uint8_t/float/double), decoded condition expressions via `_CRState` (cmpwi+branch → `if (r3 > 5) goto loc_X`), resolved PLT calls with argument register values at call site, and TOC/GOT load annotation.
- **inputs / outputs:** Input: text bytes + text VA + PLT dict + exports dict + optional strings dict (via from_context). Output: C-like pseudo-code function body with opening/closing braces and local declarations.
- **scope:** PPC32 BE, documented for IBM PPC476 Book E (glibc-2.15). Handles Book E privileged/cache/TLB instructions as pass-through comments. Does not handle Altivec/VMX.
- **status:** implemented — this is the substantive decompiler; Ppc476Lifter is the simpler predecessor.
- **evidence:** No dedicated test file found.
- **docs:** `ppc32-ppc476-dedicated-lifting.md` describes both classes but incorrectly states Ppc476Decompiler uses `from_context(ctx)` which it does. **Mismatch in concepts-decompiler.md:** that doc says `Ppc476Decompiler` lives at `ablation.analyzers.ppc476_lifter` — incorrect; it is in `ppc476_decompiler.py`.
- **limitations:** Linear-only through one function; does not track inter-procedural data flow. from_context reads `.text` via LIEF — fails on XCOFF32. TOC/GOT resolution requires `strings` dict pre-populated by caller.
- **dependencies:** capstone (optional), lief (via from_context), stdlib struct/collections

## 8. PPC32PLTTracer

- **name:** `PPC32PLTTracer`
- **category:** Verified PLT Import Caller Tracer
- **paths:** `ppc32_plt_tracer.py` lines 302–449
- **entry point:** `PPC32PLTTracer.from_path(path)` or `PPC32PLTTracer(elf)` then `.find_callers(sym_name) -> List[PLTCallSite]`; also `batch_sweep(directory)` and `batch_scan(directory)` module-level functions.
- **what it does:** Finds every BL instruction that calls a named imported symbol in a PPC32 BE .so, applying r30 cross-check (compares caller's actual r30 against the expected r30 implied by the PLT slot) to eliminate cross-compilation-unit false positives. Dispatches to BSS PLT path for IBM HPS/glibc SYSV PIC binaries.
- **inputs / outputs:** Input: ELF path. Output: `List[PLTCallSite]` (bl_va, thunk_va, caller_r30, func_name); `report()` returns formatted string.
- **scope:** PPC32 BE ELF; two call models: GOT2-PIC thunk with r30 verification, and SYSV BSS PLT with direct BL-to-stub scan.
- **status:** implemented
- **evidence:** `tests/conformance/test_sink_arg_classifier_ppc32.py` likely covers related logic. No dedicated PPC32PLTTracer test found.
- **docs:** `ppc32-plt-tracer.md` and `verified-ppc32-import-callers.md`; both appear accurate per code inspection.
- **limitations:** `_get_caller_r30` scans backward up to 8192 bytes. BSS PLT requires ≥2 stubs to determine resolver_size. `DANGEROUS_SINKS` is a fixed set (system, popen, execl, execve, execvp, execvpe).
- **dependencies:** capstone, lief, stdlib struct

## 10. Ppc64BeSinkClassifier

- **name:** `Ppc64BeSinkClassifier`
- **category:** Sink Argument Classifier — PPC64 BE ELFv1
- **paths:** `ppc64_be_sink_classifier.py` lines 1–647
- **entry point:** `Ppc64BeSinkClassifier.from_path(path)` or `.from_context(ctx)` then `.classify_all() -> List[Ppc64SinkSite]`; also `.classify_sink(name)`, `.add_sink(name)`, `report(results)`
- **what it does:** Classifies PPC64 BE ELFv1 BL-to-sink call sites by inspecting r3 (dest) and r4 (src/fmt) in a 12-instruction lookback window. Taxonomizes results as RODATA_TOC / IMM_SIZE / STACK_DEST / ARG_PROPAGATED / GLOBAL_DEREF / CATGETS_RETURN / IBM_OBJECT / UNKNOWN. Mirrors SinkArgClassifier taxonomy for PPC64. Detects IBM string allocator pattern (strcpyx with r4=0) and NLS catgets format-string source.
- **inputs / outputs:** Input: ELF path or BinaryContext. Output: `List[Ppc64SinkSite]` dataclasses with dest_class/src_class/interesting flags; `report()` returns table string.
- **scope:** PPC64 BE ELFv1 IBM targets (RHEL/SLES ppc64, LoadLeveler, GPFS). Default sinks: strcpyx, strcatx, strlenx, strdupx, sprintf, snprintf, strcpy, strcat, memcpy.
- **status:** implemented — **NOTE:** `_classify_site` hardcodes `file_base = 0x10000000` (standard IBM PPC64 ELF base) at line 225. This will produce incorrect results for binaries loaded at a different base address. The comment at line 217 acknowledges this as a simplification.
- **evidence:** `tests/conformance/test_sink_arg_classifier_ppc64.py` — likely covers the ELFv1 variant. No dedicated test for Ppc64BeSinkClassifier's full classification logic found.
- **docs:** `ppc64-be-sink-classifier.md` and `ppc64-be-sink-classification.md`; both appear to match code intent.
- **limitations:** `file_base = 0x10000000` hardcoded — non-IBM binaries at different load addresses will have wrong VA arithmetic. CATGETS_RETURN detection requires catgets stub in stub_map. 12-instruction lookback window may miss TOC loads farther than 12 insns from BL (documented as FORGE MEDIUM at line 355).
- **dependencies:** capstone (required; returns empty if absent), Ppc64ElfV1Resolver (required)

## 12. Ppc64ElfV1Resolver

- **name:** `Ppc64ElfV1Resolver`
- **category:** ELFv1 OPD/glink Resolver
- **paths:** `ppc64_elfv1_resolver.py` lines 1–420
- **entry point:** `Ppc64ElfV1Resolver.from_path(path)` or `.from_context(ctx)` then `.resolve() -> Ppc64ElfV1Info`; also `.patch_context(ctx)`, `.find_bl_callers(stub_va)`, `.find_all_bl_callers()`, static `.is_ppc64_elfv1(path)`
- **what it does:** Resolves PPC64 BE ELFv1 OPD section (24-byte function descriptors → code VAs) and glink stubs (.rela.plt JMP_SLOTs → stub_VA → symbol_name). Patches BinaryContext so ctx.plt maps stub VAs (not GOT slot VAs) and ctx.func_starts contains code VAs (not OPD entry VAs). Correct BL target decode included as a method.
- **inputs / outputs:** Input: ELF path or BinaryContext. Output: `Ppc64ElfV1Info` dataclass (opd_to_code, stub_map, text bounds, TOC); `patch_context` modifies ctx in-place.
- **scope:** PPC64 BE ELF64 (class=2, data=2). Handles IBM Linux POWER, AIX-style ELFv1. Glink stub mapping uses TOC-based DS-form displacement decode to handle out-of-order stubs (llstepnotify case documented).
- **status:** implemented
- **evidence:** Indirectly tested via ppc64_be_call_scanner tests which import it.
- **docs:** `ppc64-elfv1-resolver.md` and `ppc64-elfv1-resolution.md`; `sink-arg-classifier-ppc64-elfv1.md` also references it. All appear to match code. `ppc32-ppc476-dedicated-lifting.md` describes it accurately in the resolver section.
- **limitations:** Falls back to index=GOT-VA-rank if TOC-based stub decode yields nothing. Assumes glink stubs are 28 bytes each from start of .text — will fail on binaries with a different layout or prefix resolver code between stubs. Does not handle PPC64 ELFv2 (little-endian).
- **dependencies:** stdlib struct

## 13. scan_power10_stubs

## 15. PS3OPDVtableScanner

- **name:** `PS3OPDVtableScanner`
- **category:** PS3/PPC64 ELFv1 C++ Vtable Scanner
- **paths:** `ps3_opd_vtable_scanner.py` lines 1–485
- **entry point:** `PS3OPDVtableScanner.from_context(ctx, toc=None)` or `.from_path(elf_path, toc=None)` then `.scan(min_slots=3) -> List[OPDVtable]`; also `.inject_into_context(vtables, ctx)`, `.report(vtables, ctx)`, `.find_by_method_name(vtables, name, ctx)`
- **what it does:** Scans a PS3 Cell PPU binary's data segment for dense runs of 4-byte values that are valid OPD pointers (target in data → {code_va in text, toc_va = known constant}). Reconstructs C++ vtables with RTTI header detection, null-stub detection (pure-virtual placeholder), class_hint from nearest string, and multi-module TOC support (dual-TOC binaries e.g. GoldenEye). Injects resolved function names into BinaryContext.
- **inputs / outputs:** Input: BinaryContext or ELF path. Output: `List[OPDVtable]` (va, slots, method_vas, null_slots, rtti_offset, class_hint); `inject_into_context()` returns count of new names; `report()` returns ASCII table.
- **scope:** PS3 Cell PPU PPC64 ELFv1 big-endian ELF. 4-byte (32-bit addressing mode) OPD entries. Supports dual-TOC binaries via `toc_set`. Does NOT handle regular PPC64 Linux ELFv1 (which uses 8-byte OPD entries).
- **status:** implemented
- **evidence:** No dedicated test file found.
- **docs:** `ps3-opd-vtable-scanner.md` and `ps3-opd-virtual-tables.md`; both appear to match code structure.

## 16. PS3SELFDecryptor

- **name:** `PS3SELFDecryptor`
- **category:** PS3 SELF Decryptor
- **paths:** `ps3_self_decryptor.py` lines 1–360
- **entry point:** `PS3SELFDecryptor.from_path(self_path)` (auto-detect keyset) or `.from_key_rev(key_rev)` or `.register_keyset(key_rev, erk, riv)` then `.decrypt(in_path, out_path)` or `.decrypt_to_tmp(in_path) -> str`
- **what it does:** Decrypts PS3 SELF (Signed ELF) files using 3-stage AES: (1) AES-256-CBC decrypt metadata_info block with master ERK/RIV; (2) AES-128-CTR decrypt metadata header + section headers + key table; (3) AES-128-CTR decrypt each encrypted PHDR section with per-section key/IV from decrypted key table. - **status:** partial — **ONLY ONE KEYSET** (0x0016) is built-in. All other key_rev values require manual `register_keyset()` call.
- **evidence:** No dedicated test file found.
- **docs:** `ps3-self-decryptor.md` — should be checked for keyset coverage claims. The one-keyset limitation should be documented there.
- **limitations:** Single built-in keyset (0x0016). Does not handle LV2 kernel SELFs, SPU modules, or SKU-specific keysets. Padding check at stage 2 (line 226–229) raises RuntimeError on wrong keyset — error message mentions key_rev in decimal (0x0016 = 22), which is informative but the mismatch detection relies on pad bytes being zero, which is probabilistic. pycryptodome required; raises ImportError if absent.
- **dependencies:** pycryptodome (required: `Crypto.Cipher.AES`), stdlib struct/tempfile/os

## 21. Xcoff32Decompiler

- **name:** `Xcoff32Decompiler`
- **category:** Decompiler — IBM AIX XCOFF32 PPC32 BE
- **paths:** `xcoff32_decompiler.py` lines 1–833
- **entry point:** `Xcoff32Decompiler.from_context(ctx)` then `.decompile(func_va, n_insn=200) -> str`; also `.va_for_name(name) -> Optional[int]`
- **what it does:** C-like pseudocode decompiler for IBM AIX XCOFF32 PPC32 BE binaries. Extends Ppc476Decompiler semantics with AIX-specific patterns: function descriptors (sym.va in .data ≠ sym.code_va in .text), TOC-relative load resolution (`_resolve_toc`), glue trampoline decoding (lwz r0,0(r2); mtctr r0; bctr → resolved symbol call), csect local function support from XcoffSymtabParser, comprehensive instruction coverage (floating-point, rlwinm/rlwimi/rotlwi, sign-extend, clz/popcount, syscall).
- **inputs / outputs:** Input: BinaryContext for XCOFF32 binary (magic 0x01df or 0x01f7). Output: C-like pseudocode string. Validates XCOFF magic in from_context and raises ValueError on non-XCOFF. Also accepts direct constructor.
- **scope:** XCOFF32 (0x01df) and XCOFF64 (0x01f7) headers are accepted; however, the decompiler only parses 32-bit section headers. Handles PPC32 BE instruction set. Handles both XCOFF archive members and executables.
- **status:** implemented — most comprehensive PPC32 BE decompiler in the suite; substantially more instruction coverage than Ppc476Decompiler.
- **evidence:** `tests/conformance/test_xcoff_parser.py` covers the underlying xcoff_parser; no dedicated Xcoff32Decompiler test found.
- **docs:** `xcoff32-decompiler.md` — accurate match per inspection. `aix-xcoff32-64-analysis.md` and `xcoff-executable-analyzer.md` are related.
- **limitations:** XCOFF section header parsing in `from_context` uses 32-bit struct layout (40-byte entries) for both XCOFF32 and XCOFF64 (which has 72-byte entries). XCOFF64 from_context will parse wrong section offsets and likely fail silently. `_resolve_toc` requires both toc_data and toc_va; if either is missing, returns symbolic string only. TOC base detected from first export descriptor; binaries with no exports in .data return toc_va=0 and all TOC loads emit unresolved strings.
- **dependencies:** capstone (optional; required for decompile()), ppc476_decompiler (imports _Val, _RegFile, _StackFrame, _CFG, _CRState), stdlib struct
