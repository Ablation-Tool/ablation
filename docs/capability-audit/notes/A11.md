### 1. ABCParser

- **name:** `ABCParser`
- **category:** HarmonyOS / ArkTS binary format parser
- **paths:** `ablation/analyzers/abc_parser.py` lines 1–743
- **entry point:** `ABCParser.from_path(path: str | Path) -> ABCParser` ; `ABCParser(data: bytes)`
- **what it does:** Zero-copy parser for HarmonyOS Ark Bytecode (ABC) format, versions 9–13. Reads the binary ABC header, index headers, per-region class/method/string/literal index tables, and code items. Exposes class names, method metadata, code items with raw bytecode, field info, and string tables. Also provides security-oriented query methods for finding native methods, string references, and class/method lookups.
- **inputs / outputs:**
  - Input: raw `.abc` file bytes or path to file
  - Output: `ABCParser` object exposing `header: ABCHeader`, `iter_class_names()`, `iter_class_info()`, `find_native_methods()`, `find_methods_by_name(name)`, `find_methods_in_class(class_name)`, `find_string_refs_in_code(string_pattern)`, `summary() -> str`
  - `find_native_methods()` returns `List[MethodInfo]`
  - `summary()` returns multi-line stats string
- **scope:** ABC files from HarmonyOS HAP packages (`modules.abc`), individual `.abc` files, obfuscated HAP bundles. Versions v9–v13+. Handles v12.0.6.0 literal-array header boundary (`has_literal_in_header()`). Two dialects: DYNAMIC (ECMAScript, ULEB128 access_flags) and STATIC.
- **status:** implemented
- **evidence:** No dedicated test file found in `tests/`. `test_browser_extension_auditor.py` and `test_go_x86_strip_scanner.py` do not exercise ABCParser.
- **docs:** `docs/reference-modules/harmonyos.md` — describes ABCParser accurately. Warns correctly about `resolve_class_idx` vs `resolve_method_idx` for 'd'-kind operands, `has_code` check before `get_code()`, and literal-array walk for anonymous functions. Doc matches code.
- **limitations:**
  - `_scan_string_refs_in_bytecode()` is explicitly marked in code as "best-effort" with in-code comment: "A proper implementation belongs in abc_disasm.py". May produce false negatives on string refs in complex bytecode sequences.
  - `iter_methods()` covers class-body methods only; anonymous functions in literal arrays require separate literal-array walk (documented in harmonyos.md).
  - No support for ABC versions below v9 or above v13 (graceful fallback behavior on unknown versions not fully specified in code).
- **dependencies:** None (zero-dependency parser)
- **claims to verify:**
  - harmonyos.md states `ABCParser.from_path()` uses a context manager that "reads the entire file into memory" and "no file handles kept open." Code at line ~60 confirms no persistent file handle. ✓
  - 'd'-kind operands are indices into per-region tables, not raw file offsets. Confirmed in `resolve_class_idx()` and `resolve_method_idx()` implementations. ✓

### 2. ARKDisasm

- **name:** `ARKDisasm`
- **category:** ARK ISA bytecode disassembler
- **paths:** `ablation/analyzers/abc_disasm.py` lines 1–609
- **entry point:** `ARKDisasm(parser: ABCParser)` ; then `disasm_method(method, code)`, `disasm_all()`, `iter_insns(code)`, `find_calls(code)`, `find_string_loads(code)`
- **what it does:** Full 324-opcode ARK ISA disassembler producing `ARKInstruction` dataclasses from raw code-item bytes. Handles all four prefix groups (callruntime=0xfb, deprecated=0xfc, wide=0xfd, throw=0xfe) plus the base opcode table. Identifies call instructions and string-load instructions with resolved operand IDs.
- **inputs / outputs:**
  - Input: `ABCParser` instance (provides string/method/class index resolution)
  - `iter_insns(code: CodeItem)` → `Iterator[ARKInstruction]`
  - `find_calls(code)` → `List[ARKInstruction]` (is_call == True)
  - `find_string_loads(code)` → `List[ARKInstruction]` (is_string_load == True)
  - `disasm_method(method, code)` → formatted disassembly string
  - `disasm_all()` → full disassembly of all methods in the ABC file
  - `ARKInstruction` fields: `offset`, `opcode`, `mnemonic`, `operands`, `is_call`, `is_string_load`, `string_id`, `func_entity_id`
- **scope:** ARK ISA 324 opcodes across 4 prefix groups. Unknown opcodes emitted as `.data` directives rather than raising.
- **status:** implemented
- **evidence:** No dedicated test file. No test in `tests/` exercises `ARKDisasm` directly.
- **docs:** `docs/reference-modules/harmonyos.md` describes ARKDisasm briefly as part of the HarmonyOS stack. No standalone reference doc for `abc_disasm.py` found in `reference-modules/`.
- **limitations:**
  - Unknown/undocumented opcodes emitted as `.data` directives — no error raised, but silently incomplete disassembly is possible on newer ABC versions with new opcodes.
  - String reference resolution via `string_id` on `ARKInstruction` depends on ABCParser's index tables; if index parsing is incomplete for a region, string IDs may be wrong.
- **dependencies:** `ablation.analyzers.abc_parser.ABCParser`
- **claims to verify:** Doc says abc_disasm.py is the proper home for complete string-ref scanning. Code in abc_parser.py `_scan_string_refs_in_bytecode()` comment confirms this gap still open. ✓ (gap not yet closed)

### 3. ABCDecompiler

- **name:** `ABCDecompiler`
- **category:** ARK Bytecode → JavaScript-like pseudocode decompiler
- **paths:** `ablation/analyzers/abc_decompiler.py` lines 1–1099
- **entry point:** `ABCDecompiler.from_path(path) -> ABCDecompiler` ; `decompile_method(method, code) -> str` ; `decompile_class(class_name) -> str` ; `decompile_all() -> str`
- **what it does:** Lifts ARK Bytecode to readable JavaScript-like pseudocode via two-pass analysis: accumulator copy-propagation (`_propagate_acc`) followed by CFG structuring (`_structure_cfg`) using Cifuentes 1995 §6.6 algorithm to recover while loops and if/else blocks. Handles ArkTS short-circuit evaluation pattern (two consecutive conditional jumps compiled from `a||b`).
- **inputs / outputs:**
  - Input: ABC file path or `ABCParser`+`ARKDisasm` instances
  - Output: pseudocode string with JavaScript-like syntax for each method
  - `decompile_class(class_name)` returns all methods of a class decompiled
  - `decompile_all()` returns full decompilation of entire ABC file
- **scope:** ARK ISA accumulator-centric bytecode. ArkTS ECMAScript dialect and STATIC dialect. CFG structuring handles while-loop (Cifuentes Def 59) and if/else (Cifuentes §6.6.2) recovery.
- **status:** implemented (CFG structuring marked as experimental quality for complex control flow)
- **evidence:** No test file found in `tests/`.
- **docs:** No standalone reference doc found in `reference-modules/`. The harmonyos.md mentions ARKDisasm but not ABCDecompiler.
- **limitations:**
  - CFG structuring (`_structure_cfg`) handles reducible CFGs via Cifuentes algorithm; irreducible control flow (rare in ArkTS but possible from obfuscation) may produce incorrect pseudocode without error.
  - `_merge_short_circuit` handles ArkTS `a||b` compiled to two consecutive conditionals, but only one level deep; deeper boolean chains may not be fully merged.
  - Anonymous functions in literal arrays not reachable via `decompile_class()` — requires direct `decompile_method()` calls on those code items.
- **dependencies:** `ablation.analyzers.abc_parser.ABCParser`, `ablation.analyzers.abc_disasm.ARKDisasm`
- **claims to verify:** Cifuentes 1995 algorithm reference — code cites §6.6.1 Def 59 for while-loop recovery and §6.6.2 for if/else. Not independently verified; the algorithm reference is plausible for the described CFG structuring approach.

### 8. DEXLifter

- **status:** implemented
- **evidence:** No dedicated test file.

### 10. GoFuncTable (go_pclntab)

- **name:** `GoFuncTable`
- **category:** Go pclntab parser for function boundary recovery
- **paths:** `ablation/analyzers/go_pclntab.py` lines 1–256
- **entry point:** `GoFuncTable.from_binary(data: bytes) -> Optional[GoFuncTable]`; `enrich_descriptions(funcs, func_table)` utility
- **what it does:** Parses Go's embedded `pclntab` (PC line table) from raw binary data to recover function names and virtual addresses. Always embedded in Go binaries even after stripping (used by runtime for stack unwinding). Supports Go 1.12–1.15 (magic `0xFFFFFB_FF`), 1.16–1.19 (magic `0xFFFFFA_FF`), and 1.20+ (magic `0xFFFFFFF1`). `enrich_descriptions()` adds recovered function names to `funcs` dict, trying ±delta VAs to handle prologue-scanner misalignment.
- **inputs / outputs:**
  - Input: raw binary bytes containing embedded pclntab
  - Output: `Optional[GoFuncTable]`; fields: `funcs: Dict[int, str]` (VA → name), `go_version: str`
  - `enrich_descriptions(funcs, func_table)` mutates `funcs` dict in place with names from pclntab
- **scope:** x86-64 Go ELF binaries (primary). Magic detection works on raw bytes regardless of ELF structure (enables scanning even when section headers stripped).
- **status:** implemented
- **evidence:** No dedicated test file.
- **docs:** `docs/reference-modules/go-x86-strip-scanner.md` and `docs/reference-modules/go-binary-re.md` exist and likely cover this. `go-string-recovery.md` also exists. **DOC DISCREPANCY:** The module docstring in `go_pclntab.py` states the import as `from ablation.analyzers.go_pclntab import GoFuncTable` but the code comment near the docstring uses `from modules.go_pclntab` — a stale reference to the old `modules/` layout. Any doc generated from the module docstring would show the wrong import path.
- **limitations:**
  - `from_binary()` returns `None` if no valid pclntab magic found — binary may be non-Go or have unusual layout.
  - `enrich_descriptions()` uses ±delta heuristic for VA alignment; may produce wrong name associations if prologue-scanner misalignment exceeds the delta range.
  - Go 1.2–1.11 binaries not covered (magic values differ from the three supported variants).
- **dependencies:** None (standard library only)
- **claims to verify:** Pclntab always present even in stripped Go binaries — confirmed by Go runtime design (needed for stack traces). go_x86_strip_scanner.py confirms this is the approach used. ✓

### 11. GoStringResolver

- **name:** `GoStringResolver`
- **category:** Go 1.17+ AMD64 string literal resolver
- **paths:** `ablation/analyzers/go_string_resolver.py` lines 1–470

- **what it does:** Resolves Go string literals at call sites in AMD64 Go 1.17+ binaries by detecting the `lea rax, [rip+X] / mov ebx, N` register ABI pattern for string passing. ### 12. GoX86StripScanner

- **name:** `GoX86StripScanner`
- **category:** Stripped x86-64 Go ELF function boundary recovery
- **paths:** `ablation/analyzers/go_x86_strip_scanner.py` lines 1–416
- **entry point:** `GoX86StripScanner.from_path(path: str | Path) -> GoX86StripScanner` ; `GoX86StripScanner.from_context(ctx: BinaryContext) -> GoX86StripScanner` ; `scanner.scan() -> GoScanResult` ; `scanner.patch_context(ctx) -> int` ; `GoX86StripScanner.is_go_x86_64(path) -> bool`
- **what it does:** Recovers function VAs and names from the embedded `pclntab` in stripped x86-64 Go ELF binaries where `BinaryContext` returns only ~3 func_starts. Scans raw binary bytes for pclntab magic, validates pad/quantum/ptrSize fields, parses the function name table, and recovers up to ~23,396 function boundaries. `patch_context()` adds recovered VAs to `ctx.func_starts` and bulk-sets names via `ctx.set_names_bulk()`.
- **inputs / outputs:**
  - Input: binary path or existing `BinaryContext`
  - `scan()` → `GoScanResult` (cached after first call): `funcs: Dict[int, str]`, `func_starts: List[int]`, `named_funcs: Dict[int, str]`, `go_version: str`, `summary() -> str`
  - `patch_context(ctx)` → `int` (count of VAs added to ctx)
  - `is_go_x86_64(path)` → `bool`
- **scope:** x86-64 Go ELF binaries. Go 1.2 through 1.20+. Three supported magic values plus layout variants for 1.2–1.17 vs 1.18+. Fixes the "3-func_starts problem" on stripped Go binaries.
- **status:** implemented
- **evidence:** `tests/test_go_x86_strip_scanner.py` — exercises pclntab v3 (Go 1.20+ magic `0xfffffff1`) with synthetic pclntab builder. Tests name recovery and boundary extraction. ✓
- **docs:** `docs/reference-modules/go-x86-strip-scanner.md` — accurate for constructor patterns, key methods, and workflow. ✓  
  `docs/reference-modules/stripped-go-x86-64-boundaries.md` also exists.
- **limitations:**
  - x86-64 only (quantum=1, ptrSize=8 validation); ARM64/MIPS Go binaries not handled.
  - Section headers stripped: scanner searches raw bytes for magic — may produce false pclntab matches in adversarially crafted binaries (mitigated by pad/quantum/ptrSize validation).
  - `from_context()` required over `from_path()` for stripped Go ELFs (consistent with SAC non-PIE rule from MEMORY.md).
- **dependencies:** `ablation.analyzers.binary_context.BinaryContext` (for `from_context` and `patch_context`); `ablation.analyzers.go_pclntab.GoFuncTable`
- **claims to verify:** Recovers 23,396 boundaries vs 3 from BinaryContext on `fos_server` (FortiClientEMS v7.4.5) — stated in both code comment and doc. Not independently verified in this audit. Plausible given pclntab approach.

### 13. JavaJarScanner

- **name:** `JavaJarScanner`
- **category:** Java JAR/class constant-pool exec-class scanner
- **paths:** `ablation/analyzers/java_jar_scanner.py` lines 1–300
- **entry point:** `JavaJarScanner.scan_jar(jar_path: str) -> JavaJarResult` ; `JavaJarScanner.scan_zip(zf: zipfile.ZipFile, label: str) -> JavaJarResult` ; `JavaJarScanner.scan_bytes(data: bytes, label: str) -> JavaJarResult`
- **what it does:** Scans Java JAR files for exec-class API usage by parsing CONSTANT_Utf8 entries in `.class` constant pools without requiring a JVM. Requires co-occurrence of the exec-class class name AND method name in the same constant pool to reduce false positives from common method names (`start`, `exec`, `load`). Detects 4 categories: `RUNTIME_EXEC` (Runtime.exec), `PROCESS_BUILDER` (ProcessBuilder.start), `NATIVE_LOAD` (System.load/loadLibrary/mapLibraryName), `REFLECTIVE_EXEC` (Class.forName + invoke/getMethod).
- **inputs / outputs:**
  - Input: JAR path, open `ZipFile`, or raw bytes (for JARs embedded in BFF archives)
  - Output: `JavaJarResult` with `jar_path`, `class_count`, `findings: List[JavaExecFinding]`, `categories: Set[str]`, `summary() -> str`, `report() -> str`
  - `JavaExecFinding` fields: `class_file`, `category`, `api_ref`, `evidence`
- **scope:** Java `.class` files in JAR archives. CONSTANT_Utf8 pool scanning only — works on obfuscated class files if method names unchanged. Fills gap left by `PESinkClassifier`/`SinkArgClassifier` which only handle ELF/PE.
- **status:** implemented
- **evidence:** No dedicated test file found in `tests/`.
- **docs:** `docs/reference-modules/java-jar-scanner.md` exists. Not read in full but doc exists. `docs/reference-modules/java-re.md` and `docs/reference-modules/java-class-jar-parsing.md` also exist.
- **limitations:**
  - Co-occurrence check on constant pool: a class that imports `java/lang/Runtime` and separately calls `exec()` on an unrelated class would still match if both strings appear in the pool. True co-occurrence (same call site) not verified.
  - Obfuscated class files with renamed methods (not just packages) will not be detected.
  - Does not scan JAR-within-JAR (nested JAR) structures — only the top-level entries of the ZIP.
  - `NATIVE_LOAD` detection breaks early after first match per class (only reports one of `loadLibrary`/`load`/`mapLibraryName` per class).
- **dependencies:** None (standard library: `zipfile`, `struct` only)
- **claims to verify:** "Does NOT require javap, class loading, or a JVM" — confirmed by pure struct-based constant pool parser. ✓

### 16. PycBytecodeScanner

- **name:** `PycBytecodeScanner`
- **category:** Python .pyc bytecode dangerous-pattern scanner
- **paths:** `ablation/analyzers/pyc_bytecode_scanner.py` lines 1–396
- **entry point:** `PycBytecodeScanner()` constructor ; `scanner.scan_file(path, magic=None) -> PycScanResult` ; `scanner.scan_dir(root, magic=None, recursive=True) -> List[PycScanResult]` ; `scanner.scan_raw(data, magic, min_source_size, max_source_size) -> List[PycScanResult]` ; `scanner.report(results) -> str`
- **what it does:** Scans Python `.pyc` bytecode files for dangerous function-call patterns by inspecting `co_names` in the marshalled code object tree — no source decompilation required. - **inputs / outputs:**
  - Input: `.pyc` file path, directory root, or raw firmware bytes
  - Output: `List[PycScanResult]`; each has `path`, `filename`, `python_version`, `co_names: FrozenSet[str]`, `danger_hits: FrozenSet[str]`, `os_module_present: bool`, `confidence: str`, `is_clean: bool`, `error: Optional[str]`

- **scope:** Python 3.4–3.12. Three scan modes: single file, directory tree, raw firmware image. Gap: FSW-PYC-GAP closed 2026-10-16 (FortiSwitch v7 confirmed CLEAN).
- **status:** implemented
- **evidence:** No dedicated test file.
- **docs:** `docs/reference-modules/pyc-bytecode-scanner.md` — accurate; key constants, confidence classification, and API matches code. ✓  
  `docs/reference-modules/python-pyc-scanning.md` also exists.
- **limitations:**
  - `scan_raw()` validation uses magic bytes + source_size bounds + code tag (0xe3/0x63); false positives possible in data regions that happen to contain these byte sequences.
  - `open` is in `DEFAULT_DANGEROUS_NAMES` but is not dangerous by itself — may generate LOW-confidence noise; documented in code as "worth flagging for review."
  - Python 3.13+ not yet listed in `PYC_MAGICS` — new versions require manual magic addition.
  - Requires `xdis` (`pip install xdis uncompyle6`); hard dependency (not optional/graceful).
- **dependencies:** `xdis` (required; not optional — raises `ImportError` with install instructions if absent)
- **claims to verify:** xdis handles cross-version marshal parsing Python 3.4–3.12+ — confirmed in code via `xdis.unmarshal.load_code()`. ✓ `scan_raw()` magic + structural validation prevents most false positives — confirmed by code inspection of `src_size` bounds check and code_tag check. ✓
