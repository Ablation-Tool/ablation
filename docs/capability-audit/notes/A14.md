### 1. ARM32FunctionScanner

- **name:** ARM32FunctionScanner
- **category:** Function Discovery
- **paths:** `ablation/analyzers/arm32_function_scanner.py` lines 18–181
- **entry point:** `ARM32FunctionScanner.from_path(path: str)` or `from_context(ctx)`, then `.scan() -> List[int]`; `.inject_into_context(ctx) -> int`
- **what it does:** Finds function starts in stripped ARM32 ELF binaries by scanning for PUSH {rN.., lr} prologues. Handles three encoding variants: ARM32 STMFD (4-byte aligned), Thumb-2 STMDB (2-byte aligned), and Thumb-1 PUSH (0xB5 high byte). Thumb-1 is intentionally suppressed in ARM32 mode to avoid false positives from BL instruction encodings.
- **inputs / outputs:** Input: raw binary bytes + section offset/size/VA (or auto-extracted from ELF via lief). Output: sorted `List[int]` of virtual addresses. `inject_into_context()` merges new VAs into `ctx.func_starts`.
- **scope:** ARM32 ELF (little-endian), both ARM and Thumb/Thumb-2 mode. ELF only (not PE/raw).
- **status:** implemented
- **evidence:** No test file identified in audit. Gap: no unit test against known-good stripped binary.
- **docs:** No dedicated reference doc found. Not listed in flat-binary-func-start-scanner.md or similar.
- **limitations:** Does not handle Thumb interworking mode-switching mid-binary. Requires lief for `from_path()`/`from_context()`. `report()` is a static method — minimal formatting.
- **dependencies:** lief, capstone (indirect via ARM32RegAnnotator)
- **claims to verify:** Docstring claims Thumb-1 scan is suppressed in ARM32 mode — confirmed in `scan()` logic at line 98–104.

### 2. ARM32RegAnnotator

- **name:** ARM32RegAnnotator
- **category:** Register Annotation / Call-Site Analysis
- **paths:** `ablation/analyzers/arm32_reg_annotator.py` lines 37–278
- **entry point:** `ARM32RegAnnotator.from_path(path, thumb_funcs)` or `from_context(ctx)`, then `.annotate_calls(va, end_va, window, seed_args) -> AnnotationResult`
- **what it does:** Forward symbolic register pass for ARM32/Thumb binaries tracking r0-r3 (AAPCS argument registers) at BL/BLX call sites within a single function. Handles MOV Rd, #imm, MOVW Rd, #imm16, LDR Rd, [PC, #off] literal-pool loads, MOV register copies, and ADD Rd, Rn, #imm. Returns same `CallSite`/`AnnotationResult` types as `reg_annotator.py` so FuncProfiler can use it transparently.
- **inputs / outputs:** Input: binary bytes + base VA + string table + PLT map + optional set of Thumb function VAs. Output: `AnnotationResult` with `calls: List[CallSite]` and `reg_trace: List[(va, reg, RegVal)]`.
- **scope:** ARM32/Thumb, ELF only, AAPCS calling convention (r0-r3 args).
- **status:** implemented
- **evidence:** No test file identified in audit.
- **docs:** Referenced as used by FuncProfiler for ARM32 arch. No standalone reference doc found.
- **limitations:** Linear pass only — does not follow branches or loops. Pool literal dereference limited to .text/.rodata/.data/.data.rel.ro sections. PLT offset assumes standard layout (`pv + 20 + i * 12`); may fail on non-standard PLT stubs.
- **dependencies:** capstone (CS_ARCH_ARM), lief
- **claims to verify:** Docstring says r12 is clobbered after call — confirmed in `annotate_calls()` line 257 where `_ARM32_CALLER_SAVED` includes r12.

### 3. ARM64FgetsFdDiscriminator

- **paths:** `ablation/analyzers/arm64_fgets_fd_discriminator.py` lines 62–187

For each fgets-sourced finding, traces the FILE* argument's provenance (fopen/socket/fdopen) with a forward symbolic pass over the function's instructions. - **docs:** `file-versus-socket-input-discrimination.md` in reference docs (title match). Not read in this pass.
- **limitations:** Linear forward pass — no loop handling. Does not track stack-spilled FILE* through multiple stack frames. `ldp` instruction clears class state rather than propagating. Non-fgets findings receive `fd_class="n/a"` (not "unknown").
- **dependencies:** `insn_arm64.from_capstone`, `taint_tracker_arm64.ARM64TaintTracker`

- **docs:** `caller-arg-resolver.md` exists in reference-modules. Content not re-read in this pass.
- **limitations:** Looks back at most 100 instructions from call site. Does not follow pushes through inner function calls. Does not handle tail-call patterns. x86_32 only.
- **dependencies:** capstone (CS_ARCH_X86/CS_MODE_32), lief

### 5. HashAlgoDiscriminator

- **name:** HashAlgoDiscriminator
- **category:** Crypto Pattern Detection
- **paths:** `ablation/analyzers/crypto_pattern_detector.py` lines 108–195
- **entry point:** `HashAlgoDiscriminator(binary, load_addr)`, methods: `.extract_constants(va, size) -> List[(va, val)]`, `.scan_function(va, size) -> HashAlgoMatch`, `.identify(constants) -> HashAlgoMatch` (static)
- **what it does:** Identifies hash algorithms (MD5, SHA-1, SHA-256, SHA-512, CRC32) from K-table and IV constants found in compiled ARM32/Thumb2 code. Extracts 32-bit constants via MOVW/MOVT pairs and LDR-PC literal-pool loads, then matches against precomputed signature tables. Resolves SHA-256/SHA-512 ambiguity via SHA-512-unique lower-half constants.
- **inputs / outputs:** Input: raw binary bytes + load address. Output: `HashAlgoMatch` with algo name, confidence 0-100, list of `ConstMatch` (va, value, name, algo).
- **scope:** ARM32/Thumb2 code only (uses capstone CS_ARCH_ARM/CS_MODE_THUMB). Capstone 5.x compatibility note in code for MOVW vs MOV decode difference.
- **status:** implemented
- **evidence:** No test file identified in audit.
- **docs:** `crypto.md` exists in reference-modules. Content not re-read in this pass.
- **limitations:** Thumb2 disassembly mode hardcoded — does not handle ARM32 mode constants. SHA-256/SHA-512 disambiguation works only via SHA-512 lower-half constants; cannot distinguish if lower-half constants are absent.
- **dependencies:** capstone (CS_ARCH_ARM/CS_MODE_THUMB)
- **claims to verify:** Docstring claims SHA-512 unique lower-half constants resolve ambiguity — confirmed at `_match()` lines 189-190.

### 6. CustomCBCDetector

- **name:** CustomCBCDetector
- **category:** Crypto Pattern Detection
- **paths:** `ablation/analyzers/crypto_pattern_detector.py` lines 248–395
- **entry point:** `CustomCBCDetector(binary, load_addr)`, methods: `.scan_range(va, size) -> List[CBCPattern]`, `.scan_function(va, size) -> Optional[CBCPattern]`
- **what it does:** Detects hand-rolled AES-128-CBC patterns in ARM32 Thumb2 binaries by scoring loop bodies against four structural signals: BL inside backward-branch loop (40 pts), 16-byte XOR (30 pts), MOV chaining register update (20 pts), pre-loop IV load from .rodata (10 pts). Patterns scoring ≥50 returned. Deduplicates by loop start VA.
- **inputs / outputs:** Input: raw binary bytes + load address. Output: `List[CBCPattern]` with outer_func_va, block_func_va, chaining_reg, iv_va, iv_bytes, xor_va, loop_va, confidence.
- **scope:** ARM32 Thumb2 only.
- **status:** implemented
- **evidence:** No test file identified.
- **docs:** `crypto.md` in reference-modules.
- **limitations:** Minimum confidence threshold 50 hardcoded. IV detection requires non-zero 16-byte block; all-zero IVs not detected. VEOR (vectorized XOR) requires `ARM_INS_VEOR` constant presence in installed capstone.
- **dependencies:** capstone (ARM/Thumb mode)
- **claims to verify:** Confidence threshold 50 — confirmed at `scan_range()` line 297.

### 8. DynamicSandbox

- **name:** DynamicSandbox
- **category:** Dynamic Analysis / Behavioral Evidence
- **paths:** `ablation/analyzers/dynamic_sandbox.py` lines 242–486
- **entry point:** `DynamicSandbox.from_path(binary_path, arch)` or `from_context(ctx)`, then `.run_function(va, args, max_insns) -> SandboxResult` or `.probe_multiple(va, input_sets) -> List[SandboxResult]`
- **what it does:** Unicorn-based sandbox that executes leaf functions with controlled register inputs and captures output register state and memory writes as behavioral evidence. Maps ELF LOAD segments (or PE sections) into Unicorn memory, installs PLT/IAT abort hooks, sets a halt page as return address, and snapshots/restores state between runs.
- **inputs / outputs:** Input: binary path + arch string + optional dict of register→value args. Output: `SandboxResult` with input_regs, output_regs, return_value, executed_insns, memory_writes (capped at 256), aborted flag, abort_reason, arch.
- **scope:** arm64/aarch64 (full) and x86_64/x86 (full). la64 and mips64 are NOT supported — `_init_unicorn()` raises `ValueError` for unsupported arches. Both ELF and PE formats supported.
- **status:** implemented — **this is a real Unicorn-based sandbox, not a stub**. Requires `unicorn` installed; raises `RuntimeError("unicorn not installed")` if absent.
- **evidence:** No test file identified. Module correctly guards all Unicorn calls with `_UNICORN_AVAILABLE` flag.
- **docs:** `dynamic-sandbox.md` exists and matches code accurately. Note: doc says "la64, mips64 — Stub architecture not yet wired" which is correct — the code raises ValueError for those arches.
- **limitations:** Snapshot only covers the first LOAD segment (`_read_all_mapped()` line 311). Memory writes capped at 256 entries. PLT abort sets x0=0 and stops but does not simulate actual return value. MAX_INSNS default 100,000.
- **dependencies:** unicorn, lief
- **claims to verify:** Doc claims "behavioral evidence strength 1.0" — the `DynamicProbeAdapter.execute()` assigns strength 0.40–0.75 (not 1.0). Minor doc inaccuracy vs code.

### 11. EnginePatternLibrary

- **name:** EnginePatternLibrary
- **category:** Game Engine Code Labeling
- **paths:** `ablation/analyzers/engine_pattern_library.py` lines 497–896
- **entry point:** `EnginePatternLibrary.default()` or `load(path)`, then `.label_binary(ctx, xg, semantic_searcher, arch, min_confidence) -> Dict[int, EngineLabel]`; `.strip_report(labels, total_funcs) -> str`; `.unlabeled(func_starts, labels) -> List[int]`
- **what it does:** Labels functions in stripped game binaries as known engine code (UE4/UE5, id Tech 6/7, Unity il2cpp, Source 2, CryEngine, Frostbite, GameMaker, cross-engine runtime) using three passes: exact string marker matching, regex pattern matching on string xrefs, and SemanticSearcher description matching. A fourth pass (Pass 2b) handles EH/metadata-embedded strings without xrefs (PS3/PPC64 stripped binaries).
- **difference from pattern_library.py:** `pattern_library.py` stores confirmed vulnerability patterns found in firmware RE engagements (sink call sites, taint paths, exploitability verdicts) and replays them across new binaries. `EnginePatternLibrary` stores known-good engine code signatures (UE4/Unity/etc. function names and their string markers) and labels them to be **stripped from** the analyst's attention — the goal is to identify what is NOT interesting. They serve opposite analytical roles: pattern_library finds targets; EnginePatternLibrary removes noise.
- **inputs / outputs:** Input: BinaryContext + optional XRefGraph + optional SemanticSearcher. Output: `Dict[int, EngineLabel]` mapping function VA → label. `strip_report()` produces coverage summary string.
- **scope:** Any architecture. String xref passes require either XRefGraph or `ctx.funcs_referencing_string()`. Semantic pass requires SemanticSearcher instance. PS3/CryEngine Cell BE sigs present.
- **status:** implemented. Seed corpus: ~65 signatures across 6 engines + cross-engine runtime.
- **evidence:** No test file identified.
- **docs:** `engine-pattern-library.md` exists in reference-modules.
- **limitations:** Confidence for string_proximity pass is capped at 0.65 (below default min_confidence 0.70) — proximity labels will be excluded by default. `ingest_from_findings()` uses `hash(title) & 0xffffff` for sig_id which can collide.
- **dependencies:** SemanticSearcher (optional), XRefGraph (optional)
- **claims to verify:** Doc claims 60-80% engine code coverage — not verified against a real binary in this audit.

### 12. FORGE

- **name:** FORGE
- **category:** Module Quality Gate + Local Module Store
- **paths:** `ablation/analyzers/forge.py` lines 338–678
- **entry point:**
  - `FORGE.audit_module(path: str) -> ForgeReport` — raises `ForgeAuditRequired` on cache miss
  - `FORGE.record_result(path, findings, summary) -> ForgeReport` — stores inline audit result
  - `FORGE.audit_source(path: str) -> ForgeReport` — source security pipeline (no LLM)
  - `FORGE.register(path, force=False) -> ForgeReport` — validate + copy to `~/.ablation/local_modules/`
  - `FORGE.load_local_modules() -> list[str]` — import all local modules at session start
  - CLI: `python3 -m ablation.analyzers.forge module|source|register|list <path>`
- **what it does:** `audit_module()` checks `~/.ablation/forge_cache.json` for a prior SAFE CODE audit result keyed on `blake2b(system_prompt)[:16]:blake2b(file_bytes)[:16]`. On hit returns `ForgeReport` instantly. On miss raises `ForgeAuditRequired` with instructions for inline audit. The 10-section SAFE CODE review is performed inline by Claude Code; results stored via `record_result()`. `audit_source()` runs a 3-phase no-LLM pipeline: SourceEntryClassifier (unauthenticated routes) → SourceSinkScanner (dangerous patterns) → SourceAuditCompressor (priority reads). `register()` validates first, then copies .py to `~/.ablation/local_modules/`.
- **FORGE 10 SAFE CODE audit sections** (from `_PROMPT_FALLBACK` in code, lines 93–109):
  1. **Scope & Assumptions** — what the module claims to do, preconditions, environmental requirements
  2. **Functional Correctness Assessment** — logic bugs, edge cases, off-by-one, incorrect algorithms; findings get severity rating
  3. **Operational Safety & Failure Modes** — exception paths, resource leaks, undefined behavior under failure; severity-rated
  4. **Reliability & Resilience Issues** — behavior under partial failures, retries, timeouts, data corruption; severity-rated
  5. **Performance & Resource Use Considerations** — CPU/memory hot paths, unbounded growth, O(n²) patterns
  6. **Maintainability & Operability Observations** — code clarity, naming, dead code, missing documentation
  7. **Data Integrity & Consistency Risks** — corrupt state from concurrent access, partial writes, transaction hazards; severity-rated
  8. **Testing & Verification Suggestions** — what tests are missing, what inputs to probe, fuzz targets
  9. **Prioritized Production Readiness Checklist** — ranked list of must-fix items before commit/deploy
  10. **Residual Risk & Limitations** — what the audit cannot verify, known unknowns, deployment context gaps
  After section 10, the model appends a `FORGE_JSON:` block with machine-parseable findings (severity, category, title, location, description, recommendation, cwe).
- **inputs / outputs:**
  - `audit_module()`: path → `ForgeReport` (or raises)
  - `record_result()`: path + findings list (ForgeFinding or dict) + summary → `ForgeReport`
  - `audit_source()`: repo path → `ForgeReport` with CRITICAL/HIGH/MEDIUM/LOW/INFO findings
  - `ForgeReport.gate_passed`: `True` if no CRITICAL or HIGH findings
  - `ForgeReport.highs()`: list of CRITICAL/HIGH findings
- **scope:** Any Python module (.py). `audit_source()` works on any language.
- **status:** implemented
- **evidence:** No test file identified in audit.
- **docs:** `forge.md` exists and is largely accurate. **One mismatch:** forge.md states the cache key uses "sha256system_prompt[:16]" but the code uses `hashlib.blake2b(system.encode(), digest_size=8).hexdigest()` (blake2b, not SHA-256). Minor inaccuracy in docs.
- **limitations:** `gate_passed` is purely severity-based — no minimum finding count check. SOP file fallback `_PROMPT_FALLBACK` omits the DEV & TEST ORCHESTRATION PLAN section. Cache `raw_text` is not persisted (documented in code as "too large").
- **dependencies:** `source_ingestion.SourceContext`, `source_entry_classifier.SourceEntryClassifier`, `source_sink_scanner.SourceSinkScanner`, `source_audit_compressor.SourceAuditCompressor`
- **claims to verify:**
  - "gate_passed is True when no finding has severity CRITICAL or HIGH" — confirmed: `ForgeReport.gate_passed` property line 236.
  - forge.md claims "sha256" hash for cache key — **REFUTED**: code uses blake2b (lines 141-143 in `_ForgeCache._key()`).

### 15. I386AbsoluteXrefScanner

- **name:** I386AbsoluteXrefScanner
- **category:** Cross-Reference Analysis (i386)
- **paths:** `ablation/analyzers/i386_absolute_xref_scanner.py` lines 92–end
- **entry point:** `I386AbsoluteXrefScanner.from_context(ctx)` or `from_path(path)`, then `.scan_full() -> XrefResult`; `.inject(ctx) -> int`
- **what it does:** Scans i386 ELF32 .text for 4-byte little-endian absolute values that match known string VAs. Attributes each hit to the enclosing function. Fills the gap where RIP-relative xref scanner finds almost nothing in i386 code (21 xrefs vs hundreds expected). Uses numpy vectorized scan if available, else pure Python.
- **inputs / outputs:** Input: ELF32 path + optional BinaryContext. Output: `XrefResult` with list of (code_va, string_va) pairs. `inject()` populates `ctx._str_xref_idx` and `ctx._func_str_idx`.
- **scope:** ELF32/i386 only. Not PE32 (documented limitation — too many false positives from vtable/jump-table entries).
- **status:** implemented. Automatically called by BinaryContext for x86_32 ELF binaries.
- **evidence:** No test file identified.
- **docs:** `i386-absolute-cross-references.md` exists in reference-modules.

### 28. XorSolver

- **name:** XorSolver
- **category:** Firmware XOR Decryption
- **paths:** `ablation/analyzers/xor_solver.py`
- **entry point:** `XorSolver(path: str)`, then `.solve() -> XorSolverResult`; `.kpa_attack(max_probe, max_key_repeat_check) -> XorSolverResult`; `.guess_key_length(data, min_len, max_len) -> int`; `.recover_by_frequency(key_length) -> bytes`; `.decrypt(data, key) -> bytes`
- **what it does:** Pure brute-force XOR key recovery — **no Z3, no SMT**. Four attack methods in priority order for `.solve()`: (1) **IC + frequency** (`ic+freq`): Index of Coincidence spike detection finds key length (up to 128 bytes), then column-frequency analysis recovers key — primary method for sparse firmware flash images (~85-95% null bytes or 0xFF); (2) **KPA** (`kpa`): derives key from known firmware magic bytes (ELF, SquashFS, ext4, U-Boot, gzip, Fortinet `MPFW`/`FORTI` headers) at known file offsets, validates by entropy check; (3) **Hamming+freq** (`hamming+freq`): normalized Hamming distance between adjacent ciphertext blocks minimized at true key length, then per-column x86-64 opcode frequency scoring; (4) best-confidence winner selected. `decrypt()` applies recovered key by XOR with cycling.
- **inputs / outputs:** Input: firmware file path. Output: `XorSolverResult` with key bytes, key_length, method string (`'kpa'`, `'hamming+freq'`, `'ic+freq'`, `'none'`), magic_matched label, confidence 0.0-1.0, `.decrypt(data) -> bytes`. `AffineMapAnalyzer` (same file): white-box analysis of XOR-based encryption via GF(2) affine map reconstruction — identifies zero columns, zero rows, and non-trivial mixing.
- **scope:** Any binary blob. Magic dict includes ELF, SquashFS (LE/BE), gzip, bzip2, XZ, LZMA, ext4 (at 0x438 offset), U-Boot, cpio, RPM, Fortinet MPFW/FORTI headers.
- **status:** implemented. IC key-length method validated on 512 MB NAND x86-64 image (IC=0.953 at shift=64, 244x above random baseline) and FortiWiFi FWF_60E-v7.2.4.F ARM 256 MB NAND (IC=0.753, 192x above random baseline).
- **evidence:** No standalone test file. Two validated firmware images documented in docstrings.
- **docs:** `repeating-xor-key-recovery.md` exists. **Partially outdated**: doc describes 3 methods but code now has 4 (IC+freq is the new primary path). `solve()` priority order changed from KPA-first to IC-first.
- **limitations:** IC method requires sparse plaintext (many null bytes or 0xFF); less effective on dense code blobs. Frequency analysis uses x86-64 opcode distribution only — less accurate for ARM firmware code sections. KPA requires plaintext at known file offset. Entropy range hardcoded: 3.0–7.5 for KPA validation.
- **dependencies:** numpy (optional, for Hamming distance acceleration)
- **claims to verify:** "No Z3/SMT" — confirmed: no import of z3, z3-solver, or any SMT library anywhere in file.

### FORGE: 10 SAFE CODE sections
The inline audit covers these 10 sections (from `_PROMPT_FALLBACK`, also in `forge_system.md` when present):
1. Scope & Assumptions — what the module claims, preconditions
2. Functional Correctness Assessment — logic bugs, edge cases (severity-rated)
3. Operational Safety & Failure Modes — exception paths, resource leaks (severity-rated)
4. Reliability & Resilience Issues — partial failure behavior (severity-rated)
5. Performance & Resource Use Considerations — hot paths, unbounded growth
6. Maintainability & Operability Observations — code clarity, dead code
7. Data Integrity & Consistency Risks — concurrent access, partial writes (severity-rated)
8. Testing & Verification Suggestions — missing tests, fuzz targets
9. Prioritized Production Readiness Checklist — ranked must-fix items
10. Residual Risk & Limitations — known unknowns, deployment context gaps
Sections 2, 3, 4, 7 require per-finding Title/Severity/Location/Description/Recommendation. A `FORGE_JSON:` block at the end provides machine-parseable findings.

### FORGE gate_passed semantics
`ForgeReport.gate_passed` returns `True` when **no finding has severity `CRITICAL` or `HIGH`**. It is a Python property: `not any(f.severity in ("CRITICAL", "HIGH") for f in self.findings)`. A report with zero findings also passes. The audit runs inline in Claude Code — no subprocess, no LLM API call. Cache key uses `blake2b(system_prompt, digest_size=8)[:16] + ":" + blake2b(file_bytes, digest_size=8)[:16]`.

### dynamic_sandbox.py: Real Unicorn sandbox
`DynamicSandbox` is a **real, fully implemented Unicorn-based sandbox** — not a stub. It imports `unicorn`, `unicorn.arm64_const`, and `unicorn.x86_const`, maps ELF LOAD segments and PE sections, installs code hooks, and executes functions. Supported arches: arm64/aarch64 (full), x86_64/x86 (full). LoongArch64 and MIPS64 are unsupported — `_init_unicorn()` raises `ValueError("Unsupported arch for dynamic sandbox: la64")` for those arches.

### xor_solver.py: Brute-force only, no SMT; IC+freq is now primary
`XorSolver` uses four purely statistical methods. **No Z3, no SMT.** The `solve()` priority order is: (1) IC spike detection + column-frequency recovery (`ic+freq`) — primary for sparse firmware flash images; (2) KPA against magic-byte dictionary (`kpa`); (3) Hamming distance + x86 frequency fallback (`hamming+freq`). A fourth class `AffineMapAnalyzer` (same file) does white-box affine map analysis of XOR ciphers over GF(2). The reference doc `repeating-xor-key-recovery.md` **partially outdated** — does not document the IC method or the new priority order.

### Documentation mismatches
1. **forge.md** (lines 63-64): States the cache key uses "sha256system_prompt[:16]" — **incorrect**. The code (`_ForgeCache._key()`) uses `hashlib.blake2b(..., digest_size=8).hexdigest()` (BLAKE2b), not SHA-256.
2. **dynamic-sandbox.md**: Claims behavioral evidence strength 1.0. The `DynamicProbeAdapter.execute()` assigns strength 0.40–0.75 depending on run outcome — not 1.0.
3. **ARM32FunctionScanner**, **ARM32RegAnnotator**, **opseq**: No dedicated reference docs found.

### EnginePatternLibrary vs PatternLibrary
`EnginePatternLibrary` (`engine_pattern_library.py`) and `PatternLibrary` (`pattern_library.py`) serve **opposite roles**: PatternLibrary stores confirmed vulnerability patterns to replay across new firmware targets (finds attack surface); EnginePatternLibrary stores known-good game engine code signatures to label and exclude from manual RE (removes noise). EnginePatternLibrary covers 6+ game engines (UE4/5, id Tech, Unity il2cpp, Source 2, CryEngine, Frostbite) with ~65 seed signatures. They share no code and have separate storage paths.

### Tests
No test files were identified for any of the 25 modules audited. This is a systemic gap across the entire A14 capability set.
