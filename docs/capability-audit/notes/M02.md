## Sub-theme A: Binary-level AI/LLM security analyzers

These modules accept a BinaryContext (or binary path) and perform static analysis
of agent/LLM binaries. They follow the from_context(ctx) / scan() / report() pattern.

---

### 1. AgentAuthorityAudit

- **File:** `modules/agent_authority_audit.py`
- **Class:** `AgentAuthorityAudit`
- **Entry point:** `AgentAuthorityAudit(path)` or `.from_context(ctx)` → `.scan()` → `List[AuthorityFinding]`
- **What it does:** Maps binary PLT imports to 7 capability categories using
  `_CAPABILITY_MAP`. Detects agent type (ai_agent / web_agent / cli_agent) from
  binary string patterns in `_AGENT_TYPE_PATTERNS`. For detected agent type, flags
  any imported capability that exceeds the expected set ("authority surplus").
  For ai_agent, only `network_raw` is expected; everything else is surplus.
  Returns `[]` if agent type is `'unknown'` — not an agent binary.
- **Capability categories (7):** process_execution, file_write, network_raw,
  credential_access, system_config, memory_injection, persistence
- **Agent type detection:** ai_agent (strings: tool_use, tool_call, anthropic,
  openai…), web_agent (requests, selenium, playwright…), cli_agent (argparse,
  click, typer…)
- **Inputs:** binary path or BinaryContext
- **Outputs:** `List[AuthorityFinding]` (capability, severity, note)
- **Status:** Implemented
- **Dependencies:** BinaryContext (PLT import table)
- **Limitations:** PLT-only; misses statically linked capabilities. Agent type
  detection relies on string presence in raw binary — false positives possible
  for non-agent binaries that embed LLM-adjacent strings.

### 2. AgentObservabilityAudit

- **File:** `modules/agent_observability_audit.py`
- **Class:** `AgentObservabilityAudit`
- **Entry point:** `AgentObservabilityAudit(path)` or `.from_context(ctx)` → `.scan()` → `List[ObservabilityFinding]`
- **What it does:** Gates on 9 `_AGENT_INDICATORS` (b'tool_call', b'tool_result',
  b'function_call', etc.) to confirm binary is an LLM agent. Then checks for:
  (1) **structured_logging** — syslog/log4c/sd_journal imports; (2) **hitl_checkpoint**
  — confirm/approve/checkpoint function name patterns; (3) **audit_trail** —
  audit_open/audit_log_user_message kernel audit imports.
  Reports absences as HIGH (missing HITL) or MEDIUM (missing audit trail) severity findings.
- **Inputs:** binary path or BinaryContext
- **Outputs:** `List[ObservabilityFinding]` (check_name, severity, detail)
- **Status:** Implemented
- **Dependencies:** BinaryContext (PLT, string table)
- **Limitations:** Only detects observable audit/HITL via known C library import
  names. Custom HITL implementations or in-process state machines are not detected.

### 3. AgentToolSurfaceEnumerator

- **File:** `modules/agent_tool_surface_enumerator.py`
- **Class:** `AgentToolSurfaceEnumerator`
- **Entry point:** `AgentToolSurfaceEnumerator(path)` or `.from_context(ctx)` → `.scan()` → `List[ToolSurfaceFinding]`
- **What it does:** Regex-scans binary `.rodata` for JSON tool schema blobs matching
  `"name": "…"` + `"description"/"parameters"` pattern (DOTALL, up to 80-char name).
  Classifies extracted tool names into risk tiers:
  - **HIGH (6):** shell_execution, code_execution, file_write, process_control,
    network_request, credential_access
  - **MEDIUM (2):** web_search, file_read
- **Inputs:** binary path or BinaryContext
- **Outputs:** `List[ToolSurfaceFinding]` (tool_name, risk_tier, matched_json_blob)
- **Status:** Implemented
- **Dependencies:** BinaryContext or raw path read
- **Limitations:** Regex-based JSON blob detection; tool schemas compiled-in as
  string constants are found; dynamically generated schemas are not.

### 4. AIControlIndicators

- **File:** `modules/ai_control_indicators.py`
- **Class:** `AIControlIndicators`
- **Entry point:** `AIControlIndicators(path)` or `.from_context(ctx)` → `.scan()` → `List[AICodeFinding]`
- **What it does:** Raw binary byte scan for markers of AI-generated code.
  Three check types:
  (1) **attribution_string** — 12 explicit strings (b'Generated by GitHub Copilot',
  b'Generated by ChatGPT', b'Generated by Claude', b'Generated by Amazon CodeWhisperer',
  b'Generated by Tabnine', b'Generated by Codeium', b'AI-generated code', etc.)
  (2) **hallucinated_package** — 9 hallucinated package name byte strings
  (langchain-tools, openai-functions, anthropic-sdk-extra, gpt-utils, etc.)
  (3) **comment_pattern** — 4 regex patterns for AI-generated comment style
  (boilerplate javadoc, "This function takes/handles/validates" pattern, TODO: Add/Fix/Handle)
  All findings are MEDIUM severity (informational).
- **Inputs:** binary path or BinaryContext (path used for raw read)
- **Outputs:** `List[AICodeFinding]` (indicator_type, matched, severity)
- **Status:** Implemented
- **Dependencies:** None (stdlib only, raw bytes read)
- **Limitations:** Only detects AI markers that survived stripping. In production
  binaries stripped of debug info, comment strings are removed. Useful for
  debug builds or binaries with debug sections present.
- **Docstring claim vs code:** Docstring cites "Cornell/NYU research: ~40% higher
  vulnerability rate" — this is a claim in a comment, not verified by the module.

### 5. PromptInjectionSinkClassifier

- **File:** `modules/prompt_injection_sink_classifier.py`
- **Class:** `PromptInjectionSinkClassifier`
- **Entry point:** `PromptInjectionSinkClassifier(path)` or `.from_context(ctx)` → `.scan()` → `List[PromptInjectionFinding]`
- **What it does:** Binary-level LLM API call site classifier. Two global gate
  checks before per-function analysis: (1) any of 10 LLM host strings present
  (api.openai.com, api.anthropic.com, generativelanguage.googleapis.com,
  inference.ai.azure.com, api.cohere.ai, api.mistral.ai, api.together.xyz,
  api.groq.com, bedrock-runtime., aiplatform.googleapis.com); (2) any of 12
  system-prompt indicator strings present ("role":"system", SYSTEM:, <<SYS>>,
  [INST], system_prompt, etc.).
  Per-function: disassembles each function, resolves PLT call targets, checks
  if same function calls both `_INPUT_SOURCES` (read/recv/fgets/getenv/scanf)
  and `_HTTP_WRITE_SINKS` (send/write/curl_easy_setopt/SSL_write/HttpSendRequest).
  - **HIGH:** both input source AND http write sink in same function
  - **MEDIUM:** only one of the two
- **Inputs:** binary path or BinaryContext
- **Outputs:** `List[PromptInjectionFinding]` (func_va, func_name, has_system_prompt,
  has_input_source, has_http_sink, llm_host, severity)
- **Status:** Implemented
- **Dependencies:** BinaryContext, modules._disasm_helper.disasm_func
- **Limitations:** String/import-level analysis only. For confirmed data-flow,
  docstring explicitly directs user to TaintTracker with HTTP-write sink configured.
  Only first LLM host string match used (no multi-provider coverage in one scan).

### 7. CryptoAudit

- **File:** `modules/crypto_audit.py`
- **Class:** `CryptoAudit`
- **Entry point:** `CryptoAudit()` → `.analyze_jwt(token)`, `.scan_filesystem()`,
  `.check_tls(host, port)`, `.scan_proc_environ()`
- **What it does:** Cryptographic weakness auditor for post-compromise host analysis.
  - **JWT analysis:** Decode header/payload, check alg:none (CRITICAL, forge token),
    HS256 empty-string secret (CRITICAL, forge), 20 known-weak secrets (CRITICAL).
    `forge_jwt()` stdlib-only (hmac/hashlib/json/base64).
  - **SAML analysis:** XML parse, assertion wrapping risk detection, injection checks
  - **Key material filesystem scan:** Walks CREDENTIAL_SCAN_PATHS (/etc, /opt,
    /var, /home, /root, /private/etc, /Library) for KEY_MATERIAL_EXTENSIONS
    (.pem/.key/.crt/.p12/.pfx/.jks/.env/.secret etc.) and KEY_MATERIAL_FILENAMES
    (id_rsa, .kubeconfig, vault-token, service_account.json, etc.)
    + 5 SECRET_PATTERNS regex for hardcoded API keys/passwords/tokens
  - **PEM private key detection:** 6 PEM_PRIVATE_HEADERS byte patterns
  - **JWT pattern scanning:** JWT_PATTERN regex to extract JWTs from files
  - **/proc/environ scanning:** Reads /proc/<pid>/environ (4MB cap) for exposed secrets
  - **TLS checks:** TLS_DEPRECATED_PROTOCOLS, TLS_CRITICAL_CIPHERS_RE
- **`JWT_WEAK_SECRETS`:** 20 entries (empty string, "secret", "password", "admin",
  "key", "test", "changeme", "12345", "1234567890", "your-256-bit-secret", etc.)
- **Inputs:** JWT token string / filesystem path / host:port
- **Outputs:** `self.findings` list + per-method dicts
- **Status:** Implemented
- **Dependencies:** stdlib only (no PyJWT, cryptography, openssl — pure Python)
- **Limitations:** JWT brute-force covers only the 20 hardcoded weak secrets.
  No dictionary attack against arbitrary secrets.

### 8. api_re (run_re)

- **File:** `modules/api_re.py`
- **Entry point:** `run_re(base_url, depth='normal', focus=None)` → `APIMap`
  CLI: `python api_re.py http://target:port [--depth quick|normal|deep] [--focus FOCUS] [--fuzz-params PATH] [--output FILE]`
- **What it does:** Autonomous HTTP API reverse engineering tool.
  Phases (parallel via ThreadPoolExecutor workers=6):
  1. **Framework detection:** Header/path fingerprinting for FastAPI/Flask/Django/
     Express/Gradio/Uvicorn + GraphQL detection
  2. **OpenAPI harvesting:** 20+ standard spec paths (/openapi.json, /swagger.json,
     /api-docs, /.well-known/openapi.json, etc.); parses paths/methods/params
  3. **Path discovery:** PATH_WORDLIST (100+ entries) fuzzed with GET+POST via
     ThreadPoolExecutor(workers=30)
  4. **API version discovery:** `/v{1-5}` + `/api/v{1-5}` + 6 other patterns (OWASP API9)
  5. **Parameter injection:** 8 categories × all discovered params:
     path_traversal, pickle_rce, sql_injection, ssti, ssrf, format_string, xxe,
     prototype_pollution. Confirming signals required (PATH_ACCESS alone does NOT
     confirm sql_injection/ssti/ssrf/xxe).
  6. **JWT attacks:** alg:none, HS256 weak secrets, kid injection, jku SSRF
  7. **GraphQL:** introspection, batching, alias flooding, depth attacks
  8. **OAuth2/OIDC:** redirect_uri manipulation, PKCE downgrade, scope escalation
  9. **gRPC:** server reflection, service enumeration, gRPC-Web detection
  10. **SOAP/WSDL:** XXE in SOAP body
  11. **BOLA/IDOR:** object ID enumeration
  12. **Rate limit bypass:** IP header spoofing, path variation, encoding evasion
  13. **Webhook SSRF:** cloud metadata, internal pivot
  14. **Credential reuse:** default creds against auth endpoints
  15. **Business logic:** numeric boundary, sequence breaking, price manipulation
  16. **Shadow/deprecated versions, CORS, NoSQL, BFLA, PII, timing, evasion, WebSocket**
- **Focus modes (20):** injection, schema, state, jwt, auth, bola, oauth2, grpc,
  graphql, soap, biz, ssrf, creds, cors, nosql, bfla, pii, timing, evasion,
  websocket, shadow
- **Depth modes:** quick (phases 1-3 only), normal (1-12), deep (1-30)
- **Data models:** `Endpoint(path, methods, params, responses, notes, vuln_signals)`,
  `APIMap(base_url, openapi, endpoints, headers, auth_required, framework, version, notes, findings)`
- **Output:** APIMap object; `--output FILE` writes deduplicated findings as JSON
- **Status:** Implemented (large, complex, active network tool)
- **Dependencies:** requests, stdlib (concurrent.futures, threading, io, json, re,
  base64, time, itertools, string, hashlib, hmac, urllib.parse)
- **Notes:** Response body capped at 4MB (_MAX_HTTP_BYTES) via streaming read.
  `_dedup_findings()` deduplicates by (type, endpoint/path, param).

### 13. MMTLS Protocol FSM Extractor (proto_fsm.py)

- **File:** `modules/proto_fsm.py`
- **Entry point:** `main()` — CLI: `python3 proto_fsm.py [--so PATH] [--seed VA] [--hop-depth N] [--dot FILE]`
- **What it does:** Static FSM extraction from stripped ARM64 binaries.
  Designed for WeChat MMTLS handshake in libwechatnetwork.so (ARM64).
  4 phases:
  1. **State variable identification:** Scans .text for ADRP+ADD→BSS patterns,
     then STR of small-integer-loaded register (MOV wN, #imm ≤ 16). Second pass
     finds LDR of BSS address followed within 4 insns by a branch. Sliding window = 8.
  2. **Handshake cluster BFS:** BL-reachable subgraph from seed VAs (default depth=2).
     Default seeds hardcoded for WeChat 8.0.56: 0x111f98, 0x305020, 0x305094,
     0x304d64, 0x2ec280, 0x246364.
  3. **Transition extraction:** Finds LDR state_var → branch → BL trigger → STR state_var
     quads in cluster functions. Emits `FSMTransition(from_state, to_state, trigger_pc,
     trigger_fn, state_var)`.
  4. **FSM graph:** `FSMState` + `FSMTransition` → Graphviz DOT output;
     optionally writes to `--dot FILE`.
  `_decode_adrp()` — decodes ADRP instruction's page address from raw encoding.
  `_rn()` — canonical register name (w→x normalization, xzr for reg_id=0).
- **Data classes:** `StateVar(addr, read_sites, write_sites, observed_values)`,
  `FSMState(id, value, functions)`, `FSMTransition(from_state, to_state, trigger_pc, trigger_fn, state_var)`,
  `FnProps(va, reads_state_vars, writes_state_vars, calls_insert, calls_delete)`
- **Hardcoded target constants:** INSERT_FN=0x2ec280, DELETE_FN=0x304d64 (WeChat-specific)
- **File size limit:** 256MB (_MAX_BINARY_BYTES)
- **Inputs:** ARM64 ELF .so path, optional seed VAs
- **Outputs:** Printed state/transition tables + Graphviz DOT to stdout or file
- **Status:** Implemented (ARM64 only; hardcoded seeds limit general applicability)
- **Dependencies:** lief, capstone, capstone.arm64
- **Limitations:**
  - ARM64 only
  - Seed VAs hardcoded for libwechatnetwork.so WeChat 8.0.56 — must be overridden
    via `--seed` for any other binary
  - BSS bounds fallback hardcoded to 0x3d0000+0x20000 if no .bss section found
  - Transition state values use placeholder 0→1 generic if only one observed value

## Cross-cutting observations

### Two sub-themes, different integration paths

**Binary static analysis** (AgentAuthorityAudit, AgentObservabilityAudit,
AgentToolSurfaceEnumerator, AIControlIndicators, PromptInjectionSinkClassifier):
- All use `from_context(ctx)` pattern; integrate into BinaryContext session
- Operate entirely offline; no network required
- Callable from the standard Ablation RE workflow
